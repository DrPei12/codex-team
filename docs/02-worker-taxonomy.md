# 02. Worker 分类

## “Worker”到底是什么

在本项目里，worker 是“领取一个有边界工程责任的执行者”的通称，不是 Codex 中某一种固定 workspace，也不是某个按钮名称。

同一个 Codex 任务今天可以是实现 worker，明天可以接班成为集成 worker；一个 subagent 也可以短暂承担只读 explorer，但通常不应被当作长期模块 owner。

## 一、按执行身份分类

### 1. 用户可见的 Codex 任务

大白话：侧边栏里能独立存在的一名“项目成员”。

- 有自己的长期对话历史；
- 可以被用户直接查看和继续；
- 可以接收其他任务的消息；
- 可以拥有自己的 checkout/worktree；
- 适合跨多轮、跨阶段、需要明确责任和可追踪交接的工作。

代价是管理对象更多，需要命名、状态、归档和上下文治理。

### 2. Subagent

大白话：某个任务临时叫来的“小帮手”。

- 生命周期短；
- 通常由父任务发起和收口；
- 适合搜索代码、读文档、独立分析、小范围实现或并行检查；
- 不适合保存项目唯一记忆，也不应默认成为用户长期管理的模块成员。

它更接近父任务的内部执行能力，但并不等于普通函数工具：它仍能推理、使用工具和返回结果。把它简单说成“tool”有助于理解层级，却不能据此忽略它的自主判断和成本。

### 3. 人类 owner

用户不是系统外的审批按钮，而是最终目标、风险授权和不可逆操作的 owner。自动化不能用 worker 共识替代用户明确授权。

## 二、按历史来源分类

### 1. Fresh task

大白话：新招一名成员，只给它岗位说明和项目材料。

优势是上下文干净；风险是 briefing 不完整导致重复探索。适合边界稳定、输入 artifact 完整的任务。

### 2. Forked task

大白话：复制某个任务在当时已经知道的背景，再走另一条工作路线。

优势是启动快、共享前情；风险是把父任务的噪声、错误假设和过长历史一并复制。Fork 是历史来源，不自动决定是否共享目录或使用独立 worktree。

### 3. Handed-off task

大白话：老成员把工位、Git 状态和交接包交给新成员继续。

适合上下文轮换、从实验 worktree 回到本地 checkout、或责任转移。Handoff 必须把隐含状态变成可验证 artifact，不能只说“你接着做”。

### 4. Rehydrated task

大白话：不复制旧聊天，而是从仓库中的项目状态、决策和交接包重新恢复。

这是长期项目抵抗上下文衰减的关键方式，也是本项目未来需要验证的模式。

## 三、按 workspace 分类

### 1. 同一 checkout / 同目录

多个执行者看见同一份实时文件。

适合只读调查，或文件所有权完全不重叠的极短任务。优点是无需合并、变化立即可见；缺点是另一个任务可能在你运行测试时改变文件，Git index、构建目录和生成物也会互相影响。它不能提供事务隔离。

### 2. Managed worktree

Codex 为某个任务管理的独立 Git worktree。

大白话：每名开发者有自己的工位和分支视图。文件互不踩踏，但最终仍要合并；契约不一致、同一逻辑的冲突和测试失败不会自动消失。

### 3. Permanent worktree / 既有工作目录

用户或项目长期维护的 Git worktree，通常对应一个稳定分支或长期模块。

适合持续多天的模块 owner、复杂集成或需要固定依赖缓存的工作。代价是清理、同步和分支管理责任更重。

### 4. 主 checkout

项目的主要本地目录，通常是最终集成、用户检查或发布操作的地方。默认不让多个实现 worker 同时改主 checkout。

### 5. Projectless / 无项目任务

没有绑定既有仓库的对话空间。适合概念讨论、研究和临时产物，不适合作为正式工程状态的长期 owner。本项目就是从 projectless 对话立项后迁入正式目录。

### 6. 只读或外部环境

例如只读代码审查、远端 CI、沙箱或外部服务。它们可能提供隔离和证据，但权限、持久性与本地 worktree 不同。第一版只记录接口，不把未确认的环境能力写成默认 worker 类型。

## 四、按工程角色分类

### 主编排者

维护目标、架构、任务图、契约、风险和最终验收。它不是“什么都亲自做的超级 worker”，应把局部探索和实现分出去，把上下文留给全局判断。

### Explorer

只读定位代码、依赖、历史和风险，输出证据化地图。适合 subagent 或短任务。

### Implementer

按已稳定契约实现一个有明确文件边界的任务。可以是一次性 task 或 subagent。

### Component owner

长期负责一个模块的设计一致性、实现和本模块测试。适合保留的 Codex 任务和独立 worktree。

### Reviewer / Verifier

独立检查需求符合性、缺陷、安全或测试证据。高风险场景应与 maker 分离。

### Integrator

控制合并顺序、解决跨模块冲突、运行集成 Gate。它不应该重新实现所有模块。

### Recovery worker

在测试失败、合并冲突或事故时临时建立，负责归因、最小复现和恢复方案。

### Release owner

负责最终版本、变更记录、发布验证和可逆性。通常是高权限、低并发角色。

## 五、按生命周期分类

- **一次性**：一个原子任务，接收后归档。
- **阶段性**：一个里程碑期间存在，阶段完成后归档或转岗。
- **长期 owner**：跨多个里程碑维护模块，保持可唤醒。
- **轮换中**：旧任务只处理交接，不再接新实现。
- **已归档**：保留历史，但不进入活跃 roster 和默认消息流。

## 选择速查

| 工作 | 推荐身份 | Workspace | 生命周期 |
|---|---|---|---|
| 找出认证调用链 | subagent explorer | 同目录只读 | 一次性 |
| 实现独立支付模块 | Codex component task | 独立 worktree | 长期/阶段性 |
| 修一个局部拼写与测试 | subagent implementer | 父任务 workspace | 一次性 |
| 两种架构原型对比 | 两个 Codex task | 两个 worktree | 一次性，择优后归档 |
| 合并多个模块 | Codex integrator task | 集成 worktree/主 checkout | 阶段性 |
| 老 owner 上下文老化 | 新 task 接 handoff | 接管对应 worktree | 新长期 owner |

## 第一版原则

Worker taxonomy 要被实现成可组合的 worker card，而不是为每种组合创建一个 skill。Skills 应按用户意图和工作流触发，worker card 描述实际配置。
