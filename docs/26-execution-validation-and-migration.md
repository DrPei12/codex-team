# 26. 自适应执行设计的验证与实现衔接

日期：2026-09-14；状态：采用的实施设计，验证尚未执行。配套[执行机制设计0.1](25-adaptive-execution-design.md)与D-072。本文列明现有代码依据、可复用部分、迁移边界和验收方法，不把场景推演当作运行证据。

## 1. 当前代码与新设计的差距

核对基线：Git `485485ab3d2eef9db9c7075fa2b52221dd42b312`，本轮无运行代码改动。此前里程碑证据见[里程碑5验收](22-milestone5-acceptance.md)，适用范围不变。

| 现有位置 | 本轮实际读到的行为 | 新设计处理 |
|---|---|---|
| [rules.py](../team_runtime/rules.py) 的PROPOSAL_SCHEMA | mode固定single/multi，工作包包含write_paths；每条requirement要求非空gate_ids，Gate为argv命令 | 组织建议保留但可演进；工作以结果组织，验证支持命令、来源核对、实际操作和适当评审 |
| [engine.py](../team_runtime/engine.py) 的propose与approve | 入口围绕repository，模型指令要求工程计划与可执行Gate；approve核对digest并建立Run | 完整定义独立维护；授权边界与计划内容版本分开；执行前才按需要生成派发契约 |
| engine.request_collaboration / resolve_request | 请求绑定两个package；创建后尝试steer接收方，answer写入后即completed | 消息可读；行动请求共用Work item，先排队；回答进入result-ready，接收后才解除匹配依赖 |
| engine._execute_run / _answer_request | 按预设packages和completed依赖派发，已完成接收方可启动只读协助会话 | 动态工作与执行尝试分离；责任路由、安全工作边界和资源统一登记 |
| [store.py](../team_runtime/store.py) | SQLite实体CAS、追加事件、排他租约，各公开写操作各自提交 | 保留存储基础，增加命令内多对象、事件、回执与outbox的原子事务及代次检查 |
| engine.reconcile / replace_session | 停止态核对原生idle、后台终端和源码；接替依赖中断回执与工作笔记 | 保留核实停止和保护现场的做法，扩展到独立Attempt、未决派发、局部交接和外部动作 |
| [history.py](../team_runtime/history.py) 与现有看板 | 已有工作笔记、原始历史检索和运行观察入口 | 增加工作/尝试/版本与来源关联；状态由运行事实派生，展示计划影响与待核实项 |

差距是方向演进所需的改造，不倒推旧版违反其当时验收条件。旧固定Gate等行为在原0.2协议下继续解释；新版不能以改文档方式悄悄改变旧运行数据含义。

## 2. 内部接口与模块责任

保留现有Codex专用调用链和Python/SQLite基础。实现时先划定下列内部职责，再根据代码规模拆模块；这些不是插件对用户承诺的独立服务，也不增加其他Agent平台抽象。

| 职责 | 输入及输出契约 | 主要依据/实现位置 |
|---|---|---|
| 命令与事务 | actor、operation_id、expected revisions、动作内容；返回原子持久回执和待派发记录 | 扩展store.py，语义规则从rules.py按新版本分离 |
| 规划及协调 | 当前定义、事件增量、有效工作和证据；输出有依据的工作/计划变更 | 逐步拆分engine.py内规划与监督，允许同一会话承担多种责任 |
| 队列及分配 | 合格工作、责任、资源、停止意图；输出分配和派发准备 | 从engine._execute_run提取；消息视图不另建任务真相 |
| Codex执行与观察 | 已授权Attempt、现场、模型资源配置；返回真实会话/回合及事件关联 | 保留[Codex调用模块](../team_runtime/codex.py)，对新能力逐项资格化 |
| 接收及依赖 | 结果版本、要求、证据和接收身份；输出接收、退回或失效及影响范围 | 从集成和审查逻辑提取；代码集成仅用于代码产物 |
| 恢复及副作用核对 | 控制意图、在途动作、旧执行观察、现场；输出可恢复事实与局部阻塞 | 延续reconcile，不能靠TTL代替实际停止 |
| 原始历史与状态视图 | 同一数据源中的版本、事件和来源；输出按需上下文与可读状态 | history.py及现有Board入口 |

首版内部动作覆盖：登记消息/工作、分配并领取、记录继续位置、提交结果、接收/退回、提出并提交计划变更、请求停止、核对与恢复。每个动作只有当其条件成立才要求相应字段。调用者身份、ID、时间、revision由入口提供；语义文本不套固定问卷。具体API名称与JSON Schema在实现提交中定版，并保持0.2旧记录按原版本读取。

## 3. 两条完整场景的设计推演

### 场景A：研究方案中途变化

以下是未来实测任务的示意，不含本轮已核实的行业结论。用户委托比较工具采用方案；Team调查条件后，建议由一个成员查证关键事实、另一个成员整理比较结果，必要时协调者自己执行其中一项。研究现场可以是普通资料目录，不要求Git或可执行测试Gate。

研究者发现资料与原假设冲突，发送可读消息并请求核对，形成关联工作。接收方忙碌，请求排队；发送方记录具体等待关系并让出执行槽。核对完成后，指定接收方依据原始来源接受该结论，相关等待解除。协调者修改受影响比较条件，保留不受影响的资料，并向用户解释依据。

用户随后更改方案受众，正式定义更新，相关表达及评价标准随版本调整。运行中控制进程退出；恢复时找回待处理请求与尚未接受的结果，核对原执行已停止，再继续。最终交付比较材料、来源、取舍理由与未解决信息。验收观察是否遗漏用户新意愿、是否把草稿建议当既定需求、是否虚构来源，以及用户能否沿消息理解调整来由。

### 场景B：软件局部协作与交接

用户委托一个实际数据导入功能。方案采用明确文件所有权与必要隔离，接口工作和使用方存在依赖。使用方提出接口问题，接收方在可验证工作边界处理；一个回答不足以直接替换接口约定。协调者接受接口变化后，形成局部计划版本，只重核受影响工作，其他有效验证继续复用。

接收方会话需要替换时，系统先核实旧回合、已登记子执行和后台命令停止，保留未提交成果；新会话从当前定义、接口、现场和原始历史继续。旧执行者迟到结果只作为候选资料；不能写回新分配的有效结果。集成后运行真实导入和异常链路，按需要独立审查。验证身份与环境沿用旧版有效做法，同时检查新版队列、局部变更和恢复是否真实连通。

这两条场景都需要同一实现走通。只在软件样例里换几个文字标签，不算跨领域验收。

## 4. 可判定的协议与故障验收矩阵

所有条目当前为“未运行”。优先使用真实SQLite、多进程和临时工作目录验证程序事实；替身仅用于可控故障注入并明确标注。Codex能力与用户体验必须在真实宿主中补证。

| ID | 触发情形 | 必须观察到的结果 | 验证层 |
|---|---|---|---|
| EX-01 | 两个控制入口同时领取同一工作/Session槽 | 仅一个有效分配和派发准备，失败者有明确冲突回执 | SQLite多进程 |
| EX-02 | 同命令重复提交；同键异内容 | 前者同回执且不新增工作，后者冲突且保留原记录 | SQLite |
| EX-03 | 在状态、事件和outbox提交点注入退出 | 恢复看到全部提交或全部未提交，不能出现孤立成功状态 | SQLite及进程退出 |
| EX-04 | 原生启动成功、本地回执保存前失联 | 先查原动作；能关联则接续，无法关联则待核实，不盲目再派发 | 故障注入＋原生能力 |
| EX-05 | 一次性分享发现与需要行动的提问 | 前者保存可读消息，后者只对应一个工作；升级分类保留原message_id | 语义场景＋运行记录 |
| EX-06 | 普通请求发给忙碌成员 | 请求排队，无默认steer；明确安全边界后处理并可继续原工作 | 原生事件与现场 |
| EX-07 | A等待B、B等待A；低优先级长期等待 | 检出实际等待关系，协调形成有依据调整；不无穷催问/扩容 | 调度故障场景 |
| EX-08 | answer返回但无有效接收；接收者不是指定责任 | 下游不解锁；非法接收拒绝，合法接收与解锁同事务落地 | SQLite＋语义审查 |
| EX-09 | 局部共享接口改变，另一分支未受影响 | 只阻止受影响派发；无关输入/结果保持有效，需补证处可定位 | 版本与依赖场景 |
| EX-10 | 旧epoch提交结果、新计划已切换 | 迟到结果留档，不覆盖；复用需当前接收责任显式核对 | SQLite＋交接场景 |
| EX-11 | 控制租约到期但旧回合或后台命令仍在运行 | 不启动同现场新写入者；停止未确认显示未知 | 原生＋真实进程 |
| EX-12 | 暂停/取消与派发、计划提交或完成同时发生 | 停止后不新增send-start；既有在途执行逐项核对，真实完成不抹去，UI不提前显示已停 | 多进程＋原生 |
| EX-13 | 外部动作成功而回执丢失 | 查目标状态；成功可复用，未知仅阻塞相关动作，不盲目重发 | 本地HTTP故障服务；真实工具另资格化 |
| EX-14 | Attempt失败后修复；终态Run收到新委托 | 新Attempt/后继Run引用原记录；失败和旧接受均不可抹去 | 状态转换 |
| EX-15 | 非Git研究产物及需要来源核对的要求 | 正常登记、执行、接收；无需伪造repository、commit或argv Gate | 场景A原生全链路 |
| EX-16 | 定义变更、控制者替换、长历史分页 | 新执行者读到当前定义和相关变更，能定位原文；不只读取摘要链 | 历史查询＋恢复场景 |
| EX-17 | 预算将尽、子执行未登记或模型配置不可核实 | 不超额派发新工作；保存已知/未知用量和停止位置，不假装精确核算 | 程序预约＋原生遥测 |
| EX-18 | 相同事件重复到达，无新证据 | 无重复模型判断或重复派发；新重要事件仍能被处理 | 事件游标及调用记录 |
| EX-19 | 写产物后、登记引用前退出；旧文件被外部修改 | 未引用内容不成为当前事实；hash不符有差异证据，保护原内容 | 文件＋SQLite |
| EX-20 | 依赖已accepted，原证据随后被判失效 | 下游受影响部分进入复核；旧接受记录保留，不全队作废 | 接收版本与图 |
| EX-21 | 插件入口启动运行程序、退出、再次打开 | 实际进程及运行状态相符；退出后不承诺继续监控，重启核对在途工作 | 宿主完整链路 |
| EX-22 | UI显示待登记、处理中、结果待验与已接受 | 标签对应不同事实；用户可展开可读对话、调整理由和实际产物 | 实际界面与操作者评审 |

对于非确定性的“是否理解用户意愿”“是否需要拆工作”，记录原始委托、模型判断、用户反馈与最终结果，按任务评审；不要用固定输出句式或必须调用某工具代替效果。对无新事件重复唤醒等程序性质，可直接以调用记录给出确定结论。

## 5. 首个实现切片与完成条件

首个切片选择“可追踪协作直到成果接收，并能在中断后继续”：接入真实Codex后，以场景A贯穿工作登记、派发、忙碌队列、结果接收、一次局部变更、一次停止恢复和最终交付；场景B验证工程能力没有被跨领域改造破坏。会话数量由样例的独立工作决定，不人为要求所有项目并行。

实现顺序：

1. 完成工作/尝试/接收的版本化结构及命令事务；接入持久outbox、epoch和去重。EX-01至04、08、10、14、19、20先用可复现程序检查。
2. 完成消息到工作关联、统一队列、等待图及局部Change set，接入现有工作笔记与原始检索。验证停止竞态、接收依赖和避免重复判断。
3. 在隔离现场资格化Codex派发、接收、切换、停止、后台资源和项目绑定能力，再串联上述机制。未证实的能力用明确边界降级，不能以替身通过代替此步骤。
4. 接入可读状态与资料入口，执行两条完整场景及相关故障，保存产物、时间线、版本和用户链路证据。

采用阶段完成证据控制实现顺序，不把上述顺序变成用户每次必须操作的工作流。运行入口和安装分发最终也需验证，但本轮设计不改变已结束的实验预算、不安装发布。

首个切片完成要求：主要场景交付符合目标、相关EX场景有实际结果、失败后现场与历史可恢复、无已知重复执行或错误接收核心缺口、文档状态与证据相符。完成这个切片不等于长期可靠性或多Agent收益已经证明。

## 6. 迁移与兼容边界

0.1.x与0.2记录维持原schema解释，原始文件、运行数据库与里程碑证据不原地改写。新实现为新增数据模型显式标版本；版本号与产品定义版本分别管理。首先让旧运行可按旧语义读取，再提供有来源的继续入口。

恢复旧活动Run之前先用其原版本完成现场核对并保留快照。需要进入新机制时建立后继Run，记录旧work package到新Work item/Artifact的映射、有效证据与未知项。不能把旧completed直接转换为新accepted，不能补造旧Attempt或接收者。已经完成的旧项目仅按需引用成果，不重复运行来制造新版验收。

代码责任按变更范围串行落实；旧测试保留验证旧协议，新验证针对新语义。新的多对象事务不能用反复调用旧put“看起来像事务”；引入迁移后需用真实旧格式样本验证读取与恢复。所有新能力继续仅服务Codex，Git/worktree是领域内能力，不演化成其他平台adapter。

## 7. 成本、剩余不确定性与推进边界

程序故障验证先行，以减少让模型反复重演可判定故障的成本。真实实验必须采用当轮有效预算；此前5个百分点预算已结束，本轮未恢复实验。后续实验Session及Subagent沿用用户当前指定gpt-5.6-luna/max，运行与成本记录包括内部Subagent，不能将主任务模型与实验模型混淆。

产物质量、运行可靠性和组织收益分别结论。只有有可比输入、可见上下文、实际模型配置、重复次数及完整成本口径的对照，才讨论收益；单个成功项目不能推出节省比例。误拦截与协调开销的调优在基础正确性成立后进行，阈值不提前定成产品常数。

当前待实测能力集中在：安全切换可发生的位置、取消对子执行/后台动作的覆盖、派发丢回执后的关联、非Git现场与原生项目归属、控制进程与插件生命周期。详见[开放问题当前项](14-open-questions.md)。本轮交付是设计、来源核对和验证规划；没有新增运行能力或实验完成证据。
