# 03. 多任务编排范式

编排范式是工作流，不是 worker 类型。真实项目通常在不同阶段切换范式。

## 1. Hub-and-spoke：总编排者 + 并行执行者

主编排者完成总体设计、任务切分和契约定义，多个 worker 并行实现，结果回到主编排者集成。

适用：模块边界清楚、可并行程度高、需要保持统一架构。

风险：主编排者成为瓶颈；briefing 不完整会让错误被并行放大；所有 worker 都回报大量细节会淹没主上下文。

控制办法：结构化 task brief、稳定接口、artifact-first 回报、分层集成者。

## 2. Stage pipeline：ABC 阶段流水线

A 完成设计或数据准备，B 基于 A 的 artifact 实现，C 基于 B 的产物验证或发布。对接次数少，但每次交接包较完整。

适用：工作天然有顺序、阶段产物可冻结、后续依赖前序完整结果。

风险：前段延迟让后面全部等待；大交接包可能隐藏错误；B 发现 A 的问题时返工链很长。

控制办法：每阶段定义 contract 和 entry/exit Gate，允许轻量早期预览，不等于提前接管工作。

## 3. Contract-parallel：先定契约，再并行组件

先冻结 API/schema/接口测试，各组件 owner 在独立 worktree 并行实现，最终依靠契约测试集成。

适用：前后端、服务、插件、provider 等接口清晰的系统。

风险：过早冻结错误契约；契约测试通过但语义仍不一致。

控制办法：契约版本化、示例与负例、语义审查、兼容策略。

## 4. Component ownership：长期模块 owner

每个长期任务持续负责一个模块，跨多个迭代接受工作，模块之间通过公开契约和定期集成协作。

适用：中大型持续项目，模块知识积累有价值。

风险：任务历史过长、局部最优、知识孤岛和 owner 消失。

控制办法：项目级决策记录、轮换 handoff、交叉审查、模块健康指标。

## 5. Planner–Executor–Verifier

一个角色规划，一个或多个角色执行，独立角色验证。它把“想清楚”“做出来”“证明正确”分开。

适用：需求复杂或错误代价高的功能。

风险：每层都重复读全部上下文；验证者机械重跑执行者所有工作。

控制办法：规划产出可执行 contract；执行者提交 proof-carrying handoff；验证者按风险抽查和补足证据。

## 6. Maker–checker：双人复核

Maker 负责变更，checker 独立判断是否满足需求和安全边界。

适用：安全、权限、财务、迁移、发布和破坏性操作。

风险：checker 只是复述 maker 的结论，形成形式审查。

控制办法：checker 使用独立验收清单、差异化模型或上下文，并能拒绝证据不充分的 handoff。

## 7. Expert council：专家会审

多个任务从不同角度并行分析同一问题，由主编排者综合，而不是让它们共同编辑同一实现。

适用：架构选型、威胁建模、性能方案、产品设计等信息不确定问题。

风险：意见很多但没有决策；不同专家共享同一错误前提。

控制办法：明确评价维度、要求反例和证据、设置决策 owner 和截止点。

## 8. Competing prototypes：竞争性原型

多个 worker 在隔离 worktree 中解决同一问题，按统一 benchmark 选择或组合。

适用：高不确定算法、迁移方案、UI 方向或性能优化。

风险：成本接近倍增，合并两个原型通常比想象中困难。

控制办法：限定时间与接口、共享 benchmark、不承诺合并所有方案。

## 9. Work queue：任务池

主编排者维护一组结构相似的独立任务，空闲 worker 领取下一个任务。

适用：批量迁移、规则实现、测试补齐、文档更新。

风险：任务难度不均、重复领取、质量漂移。

控制办法：claim/lease、幂等任务 ID、统一模板、抽样复核和失败升级。

## 10. Incident swarm：故障蜂群

发生阻塞或事故时，临时并行建立日志、最小复现、最近变更、环境和回滚等调查流，由 incident owner 汇总。

适用：时间敏感且原因未知的失败。

风险：所有人同时改现场、产生互相矛盾的修复。

控制办法：默认只读调查、单一修复 owner、时间线和证据账本。

## 11. Blackboard：共享事实板

多个 worker 不频繁互相对话，而是把发现、artifact 和状态写入一个版本化的共享板，其他 worker按需消费。

适用：依赖动态出现、知识逐步汇聚的研究或复杂迁移。

风险：共享板变成无结构日志或出现并发写冲突。

控制办法：append-only 记录、schema、owner、去重和定期压缩。

## 如何选

| 项目特征 | 首选范式 |
|---|---|
| 清楚模块 + 统一架构 | Hub-and-spoke + contract-parallel |
| 强顺序依赖 | Stage pipeline |
| 长期持续迭代 | Component ownership |
| 高风险变更 | Planner–Executor–Verifier + maker-checker |
| 方案未知 | Expert council 或 competing prototypes |
| 大量同构小任务 | Work queue |
| 紧急未知故障 | Incident swarm |

## 默认不是“一种范式通吃”

本项目默认采用一个组合：

1. 规划时由主编排者统一目标与契约；
2. 实现时按模块使用 hub-and-spoke / contract-parallel；
3. 集成时切到 stage pipeline，由单一 integrator 串行接收；
4. 高风险点插入 maker-checker；
5. 每个任务内部用 subagent 处理短小局部工作。

只有在项目特征不满足时，才切换为其他范式。选择逻辑未来应由 `team-plan` skill 生成并要求用户确认，而不是隐藏在 prompt 中。
