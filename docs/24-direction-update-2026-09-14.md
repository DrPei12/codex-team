# 项目方向补充：跨领域委托、启发式澄清与Plugin交付

日期：2026-09-14。来源：用户在主任务中的四项明确补充；本文件与[项目定义v0.2](23-project-definition-v0.2.zh-CN.md)共同描述目标，冲突时以用户最新补充为准。产品目标不代表当前实现已满足。

## 用户已明确的方向

1. 接到目标后，主动了解用户的细节、意愿和想法。优先提供有背景、示例和取舍信息的选择，减少要求用户独自组织长篇回答的负担；信息也应帮助用户发现此前没有想到的可能性。
2. Team不限定业务领域或某类项目。软件开发、研究、分析、内容和规划等目标都应能够进入理解与方案形成过程；只面向Codex约束执行平台，不限制任务领域。需要外部信息、存在不确定性或时效性时必须联网检索并核对来源，不能仅凭参数记忆补齐事实。
3. 约束需要在效率、质量和自主性之间取得平衡，避免反复格式校验、无效重试、过度限制和模型借流程放弃责任。清楚描述任务、条件与资源仍然重要。
4. 保留此前对动态工作流、组织选择、协作队列、共享事实、监督恢复和真实验收的理解。产品以Codex Plugin作为安装、使用和传播单位，Skills可以作为内部组成；核心不绑定特定第三方Skill或插件。

## 待工程验证的设计建议

- 澄清时先表达已有理解，围绕影响结果的重要取舍逐步提供少量有实质差异的选项，解释适用情形、代价与推荐理由。始终允许用户组合、补充、提出新方向或委托Team决定；建议不能自动写成用户需求。探索深度随用户意愿与任务不确定性调整。
- 将用户偏好、外部事实和专业判断分开：偏好向用户了解；可检索事实由Team调查；已授权的常规专业选择自行决定。搜索证据保存来源、日期与适用条件，供其他执行者复用；私有项目信息通过已有授权的本地资料或连接获取。
- 硬性检查集中在实际执行边界：权限、敏感数据、预算、写入责任、操作身份、证据真实性及必要的正确性条件。方法选择、文件组织和日常推理尽量保留自主空间，验证强度与后果和任务风险相称。
- 程序能够无歧义修正的格式问题由程序处理；涉及含义、目标或权限的歧义不得静默改写。相同原因重复失败应诊断规则或输入，不无限重新调用模型；保留已完成的有效工作，局部补证，避免无依据重跑。
- 同时观察交付质量与控制开销：拒绝原因、误拦截、重复调用、验证耗时、返工和用户介入，依据证据校准规则，不预设统一的最优阈值。
- 跨领域采用共同的目标、工作、产物、证据和责任概念；Git/worktree及代码测试用于适用场景，不作为所有任务的前提。可承接理解和规划不等于承诺工具、数据或权限未具备的操作已经可执行。
- Plugin提供统一入口与打包分发，内部按需包含Skills、Team运行程序和界面。是否增加Team自身MCP工具根据实际集成需求验证，不因采用Plugin就强制引入服务或第三方依赖。

## 当前实现与后续衔接

已有0.2 Auto运行时仍以Git工程、工作包和原生执行为主要验证范围。此前里程碑5证据继续按原条件成立，不能代表新版跨领域入口、启发式澄清和统一队列均已完成。已有构建脚本能够生成Plugin包及本地marketplace目录；新交互与调度能力、安装后的实际体验仍需实现和验证。

先更新定义及验收映射，再设计澄清流程、最小工作模型和约束分层，随后用范围明确的真实场景验证。此前5个百分点实验预算已用完，本次方向记录不恢复模型实验、不安装或发布插件。
