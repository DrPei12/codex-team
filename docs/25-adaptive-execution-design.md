# 25. 自适应执行、协作队列与恢复设计

设计版本：0.1；日期：2026-09-14。依据：[正式项目定义](project-definition.md)、D-070至D-072，以及用户“就按你的建议设计吧”的明确委托。

本文是当前采用的设计基线，尚未实现。用户已接受总体责任明确、局部执行自主、动态计划和可追踪协作等原则；下文的数据关系、状态语义和实现顺序由主任务据此设计，不把每个技术细节写成用户逐项指定。字段名用于解释内部契约，最终序列化格式在实现时定版，不约束用户或Agent的表达方式。验收场景与旧实现迁移见[设计验证与实现衔接](26-execution-validation-and-migration.md)。

## 1. 组织责任与程序边界

Team保留一个明确的总体协调责任，负责整体目标、跨工作取舍与最终交付。它可以由当前主会话承担，也可以在可靠交接后换人；需要时将局部协调委托给某个成员。小任务允许同一会话兼任协调和执行，不为角色完整性强行创建额外会话。执行者可以直接向相应责任方提问、协作，协调者不转述所有消息。

模型决定接下来做什么、为什么做、谁适合承担，以及结果是否符合目标。运行程序负责持久记录、派发、约束落实和原生执行观察。确定性事件不默认调用模型；目标变化、真实阻塞、关键成果、依赖冲突或缺乏有效进展的证据触发相关判断。Coordinator的语义责任与控制进程的排他执行租约是两件事，模型不需要持续运行才能保有协调责任。

| 事项 | 执行者自主范围 | 总体或受委托协调者 | 程序落实 |
|---|---|---|---|
| 调查、方法选择、局部实现和必要验证 | 在当前目标、资源与写入范围内自主完成 | 发现整体偏差时纠正 | 校验实际权限与资源，不审核每步推理 |
| 创建协助请求、分享发现 | 可直接面向责任领域提出 | 处理无人负责、优先级冲突与长期等待 | 登记、路由、去重，维护队列 |
| 执行顺序 | 在已授权分支和同等优先级内选择 | 调整跨工作优先级、关键依赖 | 不派发依赖未满足或责任冲突的工作 |
| 调用Subagent | 仅在已有委托与资源允许时选择 | 配置和调整团队内分工 | 登记实际载体、权限和资源，不能隐形扩容 |
| 修改共享接口、转移所有权、改变依赖 | 提出带依据的变更，也可按已授权局部协调范围处理 | 对跨范围影响作出决定 | 版本化变更，确认交接，检查冲突 |
| 采纳局部结果 | 作为指定接收责任人时可以判断 | 负责跨工作结果与最终交付 | 绑定输入和产物版本，按有效接收解锁依赖 |
| 更改用户目标、重要偏好或超出授权 | 说明影响与建议 | 按最新用户输入处理；缺少必要授权时提出最小问题 | 外部文本和模型声明不能扩大授权 |
| 停止与权限撤销 | 可报告局部风险并请求停止 | 处理受影响范围和后续方案 | 控制通道先限制派发，核实停止事实 |

接受条件根据任务需要建立，不能为方便运行而削弱。审查独立性按风险确定：已要求独立审查的工作不能由原作者冒充独立接收者；轻量工作允许指定负责人在同一轮完成执行与接收记录。

## 2. 逐步展开的执行方案

正式运行前，Team给出整体推进思路、近期可执行工作、主要依赖、不确定性、组织理由和交付检查点。远期工作可以先保持意图描述，调查结果足够时再展开。每次新增执行工作均说明其对当前目标的作用，防止探索变成无关扩展；不把所有思考或工具调用编排成任务节点。

工作图使用带版本的工作与依赖记录。队列、任务图和成员视图从同一记录派生；不再维护一份另有真相的调度脚本。第一版选择声明式工作记录及受控变更命令：模型在关键事件后增补、调整工作，程序执行确定的领取、等待、接收与停止规则。暂不另建通用工作流语言或任意编排代码执行器；未来确有表达缺口时再通过实测扩展。

依赖包括要求采用有效成果的硬依赖，以及仅提供背景、不阻止启动的参考关系。硬依赖明确指向可接受的结果条件，调度时绑定具体已接受版本；启动后的输入不能随“最新”指针静默改变。草稿可以作为标明不确定性的探索输入，但不能冒充已接受结果解除硬依赖。运行中的依赖图与新增等待关系都检查循环；发现语义循环，由协调者拆出最小解除阻塞工作或修订依赖，不让程序自行编造替代结果。

## 3. 工作身份、执行尝试和产物

以下是逻辑对象，并不要求各有一个独立文件、服务或用户表单。程序自动生成ID、时间、版本和调用身份，Agent只需提供当前动作所需的语义内容。

| 对象 | 核心含义与最低信息 | 所有权与版本 |
|---|---|---|
| Project | 长期目标及资料空间；正式定义引用、当前总体责任 | 不等于Git仓库或Codex侧栏项目；原生projectId仅在实际创建并读回后绑定 |
| Run | 当前授权范围内的一轮推进；交付点、授权引用、资源、运行状态 | 项目可以有多轮；本设计首版同一项目保留一个活动Run，局部并行在其内部进行 |
| Plan revision | 当前工作、责任、依赖及组织安排的版本；原因和前驱 | 不可变变更记录加当前指针；仅受影响工作切换 |
| Work item | 要取得的结果；目标关联、责任领域、输入、必要边界、预期产物和接收依据 | 稳定work_id；执行、协助、修复、审查共用此对象，kind仅用于组织视图 |
| Assignment | 谁当前承担哪项工作；执行范围、授权引用及责任代次epoch | 同一工作版本最多一个当前有效执行分配；转移时保留旧分配 |
| Attempt | 某次实际执行；assignment、输入绑定、会话/回合及结果 | attempt_id独立；重试产生新尝试并说明原因，终态不重开 |
| Message | 可读正文、发送者、讨论关联、材料引用 | 原文追加保存；需要行动的消息关联唯一work_id，无需另建一套请求状态 |
| Artifact / Evidence | 实际成果及核验依据；版本、来源、适用输入和环境 | 内容更新产生后继版本；外部可变链接附观察时间，必要时保存可合法保存的快照 |
| Acceptance | 谁依据什么接收或退回哪一版结果 | 同时绑定工作要求、结果和证据；失效保留原判定与原因 |

只有需要独立产出、责任交接、持续等待或单独核验时才拆工作。创建候选工作时可以暂缺执行者或材料；派发前必须具备可用输入、明确执行范围、接收依据和授权。只读工作无需制造写入路径或Git提交，研究也无需制造测试命令。范围可以通过已有正式定义和契约引用获得，避免把完整项目复制进每个brief。

同一工作在目标与接收条件未变时，可以有多个先后尝试；条件实质变化则增加work_revision并保留原记录。任务拆分产生子工作，旧范围由版本化计划替代，防止父子重复计入交付。已接受工作出现新需求时建立后继工作，复用旧成果；发现原结果失效则新增失效记录和修复工作，不能擦除曾经的接收事实。

## 4. 可读消息、统一队列与工作切换

纯信息消息保存原文并按需合并通知；需要别人作出行动或提供会阻塞后续的回答，登记为Work item。快速回答可以在同一轮形成结果并接收，但仍保留关联。如果提问起初被当成信息、后来形成承诺或依赖，沿原message_id补建工作，不丢失对话来由。分类由模型按语义判断，程序不靠关键词或消息长度决定。

请求面向责任领域或已指定的责任人。具体Session绑定发生在分配时，原负责人离开后请求仍然存在。提交得到“已登记”回执；分配、送达、接收和执行各自有事实依据。普通请求不直接调用原生steer注入忙碌回合，也不因队列非空自动创建新Session。

处理顺序先满足有效授权、可用输入、资源和所有权，再考虑用户优先级、能解除的关键阻塞、等待时间与上下文切换代价。执行者可在同等优先级的合格工作中选择；跨范围冲突或持续饥饿触发协调。优先级理由可读，成员的“紧急”标签不能自行取得无限插队权。阈值在验证中校准，不预设统一最优等待时长、并发数或消息频率。

每个Session同时执行一个主责任。处理独立协助前，原工作必须完成、明确等待或交还当前执行槽。安全边界需同时具备执行者保存的继续位置和程序可观察的回合/命令状态；一次测试完成的自报不证明后台动作停止。若原生能力只能在回合结束后安全切换，首版就采用回合结束边界；回合内可靠让出、恢复属于能力验证项。切换后恢复原工作时重新核对相关定义、依赖和现场变化。

双方相互等待时，运行程序登记等待边并停止无意义重复唤醒。协调者可以澄清争议、缩小请求、安排有权的只读查证或重划工作。所有等待都说明等待对象、原因及触发继续的事件；依赖释放只唤醒相关工作。小通知合并到下一次相关处理，不在用户界面强制展开全部会话。

## 5. 状态模型与接收语义

状态分别描述工作、实际尝试、消息投递和控制意图，界面不将它们折叠成一个真假难辨的“进行中”。以下是内部首版设计，不是用户操作步骤。

| 工作状态 | 进入依据 | 合法后继与限制 |
|---|---|---|
| queued（已登记待安排） | 工作已持久化，可尚缺责任或依赖 | 分配后assigned；等待条件、取消或拒绝按原因记录 |
| assigned（已分配） | 分配及范围已提交 | 明确接收后acknowledged；无人接收时可撤销分配并重新排队 |
| acknowledged（已接收） | 可信调用身份确认接收 | 派发确认后working；接收不证明已经执行 |
| working（处理中） | 当前尝试有原生开始依据 | waiting、paused或result-ready；尝试失败进入等待恢复判断，确认不再继续才结束工作；未确认派发单独标待核实 |
| waiting（等待条件） | 存在具体等待对象或依赖 | 条件满足并核验后继续；等待本身不记失败 |
| paused（已确认暂停） | 受影响执行已停止且现场已核对 | 原工作可恢复，新原生回合产生新Attempt；历史尝试不重开 |
| result-ready（结果待验证） | 对应尝试提交了可定位结果 | 接收为accepted；退回补证或修复则重新排队，保留原因并新建尝试 |
| accepted（已接受） | 有效Acceptance覆盖当前结果与接收条件 | 解锁匹配依赖；后续改变用新工作或失效记录表达 |
| failed / rejected / canceled | 分别为决定结束工作、未承接或已确认取消 | 不静默复活；继续通过有来源的后继工作表达 |

一次Attempt失败不会自动结束整个Work item。恢复判断可以选择在同一工作下新建尝试；决定不再继续时才把工作置为failed。语义和条件未变化的result-ready退回可在同一工作下补证或修复，旧结果与判定不删除。waiting的原生回合若仍在等待输入，可在核验后续接；若回合已经终止，创建新Attempt继续相同工作。

Attempt记录prepared、dispatching、running、waiting，以及succeeded、failed、interrupted、canceled、not-started等终态；状态不明时额外标记needs-reconciliation，不能推断成功或停止。准备完成不等于派发成功。停止请求是control intent，作用于Run或受影响工作，不覆盖尚未核实的执行事实。

消息投递分别记录pending、sent、observed以及不确定结果；它们不等于工作接收。命令的调用者身份来自运行通道及已登记分配，不信任正文中的“我是负责人”。收到结果后核对work_revision、attempt、分配epoch、实际输入和产物身份。过期分配的结果保留为迟到资料，禁止自动覆盖；若有价值，由当前负责人核验并显式引用为新候选证据。

新计划不令所有旧结果自动失效。只比较其绑定的目标条款、接口、输入和责任是否改变；无关计划变更保持结果有效。已接受上游材料被替代时，运行程序按已登记依赖标记受影响下游待复核，协调者处理语义影响；缺少完整依赖时不能宣称影响分析完整。

接收回执可以由已绑定的Team执行入口在持久领取时产生，并与派发准备合并在一次程序事务中；它不表示模型已阅读和理解全部材料。不要求模型为每次登记、接收、开始分别进行独立回合。原生调用开始、结果生成和接收结果必须保持可区分的证据。

## 6. 版本化调整与授权的关系

| 变化 | 处理方式 | 用户参与 |
|---|---|---|
| 当前范围内换方法、补充调查、执行既定修复分支 | 更新工作笔记及必要证据；无需重编全局计划 | 重要进展时告知 |
| 调整依赖、责任、接口或既有额度内分配 | 提交带影响说明的Change set，形成Plan后继版本 | 已有授权内自主推进，解释重要影响 |
| 已获用户确认的目标或偏好变化 | 先更新正式定义，分析影响，再切换相关执行 | 按真实用户输入采纳，不再索要写文档许可 |
| 新目标含义有冲突、敏感或破坏性影响未授权、超出预算 | 保存现有成果，暂停相关动作并提出最小问题 | 取得缺少的意愿或具体授权；无关工作可继续 |

Change set包含base_revision、原因、受影响工作、责任/输入变动、可复用产物和失效依据。程序检查版本与授权，再冻结受影响的新派发；核验旧执行停止或交还相应现场后，提交新责任和有效计划指针，派发新工作。每一步保存转换记录和恢复位置。若处理期间又收到用户停止，停止优先，未启用的候选计划保持可见。

计划更新与跨进程停止不可能靠单个数据库事务同时完成。使用prepared、quiescing、committed等内部转换记录追踪实际进度；进程崩溃后从未完成转换核对，不提前宣称新所有权已生效。无关工作的分配与输入不改动。正文或显示顺序等非语义变化可产生文档修订，不触发执行中断。

局部命令比较实际相关的工作、分配、输入和授权版本，不能仅因全局计划序号变化就拒绝无关成员的有效结果。并发Change set以当前版本重新检查受影响集合；可明确判定互不重叠时由程序重建基线，存在语义冲突时才调用协调判断。任何自动合并都保留原建议及重核依据。

授权保存目标、动作范围、资源条件、交付点和来源，计划通过引用使用授权。计划digest用于识别内容及审阅对象，不把所有计划修订都解释为授权失效。程序只自动判断明确可判的范围包含关系；需要语义判断时由有相应责任的模型说明依据并记录，不能把合法性判断伪装成散列校验。外部网页、产物和Agent消息不构成新增用户授权。

## 7. 当前事实、原始历史与可靠写入

正式定义、接口和证据保持可读、可版本化的原始内容；SQLite保存运行事实、责任、队列、事件、有效版本引用和待投递动作。定义的文件/Git版本是语义来源，数据库保存经接受的准确引用，不另存一份可独立修改的目标真相。运行数据通过受控事务修改；看板、brief和工作笔记只引用或派生它们。工作笔记允许表达判断和疑问，但不能凭一句“已完成”覆盖运行证据。

定义或大型产物先写入新的不可变内容并核对hash，再在数据库事务中引用；提交引用前崩溃产生的未引用内容留待核对，不成为当前事实。不要让数据库引用尚未可靠保存的文件。已接受原文之后被人工修改时保留差异并触发整理，不能静默改写旧证据的含义。非Git领域可以采用文件版本和内容标识，不强制用户创建代码仓库。

核心命令一次提交以下内容：调用去重键与请求摘要、预期版本检查、状态及责任变更、顺序事件、待派发动作和可重复返回的回执。它们需要同一SQLite事务，现有分开的put/append_event不足以直接保证这一点。相同去重键与相同内容返回原回执；键相同而内容不同返回明确冲突，不能悄悄当新请求。

待派发动作采用持久outbox，由控制程序投递并保存原生关联与观察结果。外部投递与本地提交之间仍可能崩溃：有经验证的原生去重/查询能力时按原operation_id核对；没有可靠对应关系时进入待核实，禁止盲目再次创建会话、回合或副作用操作。目标是可核对的重试与去重，不声称获得跨所有工具的exactly-once保证。

派发开始以事务内的send-start记录为边界：检查当前停止意图、分配代次和资源后，才从pending进入在途状态。停止提交以后不能产生新的send-start；已经进入在途的外部调用可能晚于停止才生效，必须纳入中断和核对，不能算“从未派发”。仍在pending的outbox由停止事务或后续带停止检查的领取阻止投递。

控制进程领取带代次的领导责任，所有受控写入及派发均校验当前代次；Session工作分配有独立epoch。失去租约的控制者不能继续提交新动作。但数据库拒绝旧写入不能停止已经运行的模型、shell或远程操作；恢复仍需核对它们，不能仅凭租约过期分配同一可写现场。

当前可变运行实体与事件日志由同一事务维护一致性，日志保存转换依据和恢复所需变更。第一版不以建设通用事件溯源框架为前提，也不承诺仅靠事件正文就能重建所有私有文件；备份和恢复包含数据库、实际产物及引用内容。检索带project/run/work、版本、时间和原始位置，保留分页/游标与来源归属，避免把全量历史灌进每个Agent。

## 8. 停止、恢复与外部动作

停止先持久化意图并阻止受影响的新派发，再请求中断，核对原生回合、已登记Subagent、后台命令和共享资源。界面分别显示“已请求停止”“仍有执行待确认”“已确认停止”。无法观察的部分明确标未知并限制相关接管；不同任务可以采用不同范围的停止，用户全队停止则覆盖所有已登记执行载体。

停止与完成同时到达时，仍保存真实完成回执和产物，停止意图继续约束后续派发。完成的Attempt不为迎合取消请求改成canceled，工作结果是否接收按当前目标和有效权限另行判断；用户要求停止后，不为新增业务评审继续启动模型。已接受工作不能因稍晚到达的取消请求擦除接受事实，回执说明已完成及实际受影响范围。

恢复按以下关系进行核对，顺序可由依赖调整，证据不能缺省：

1. 读取当前定义、授权、运行版本、未完成转换和最后已确认事件；取得控制责任，并核对是否仍有旧控制者或原生执行。
2. 查明在途派发、回合、命令及外部动作；保存已经发生的结果，不从进程idle推断业务完成。
3. 核对实际产物、写入边界和输入变动；保留未提交内容及现场快照，不以clean要求删除用户成果。
4. 对每项工作分别决定继续原会话、新建尝试、移交或保留阻塞；补齐队列与依赖状态，再开始合格工作。

原生等待输入、回合正常结束和控制器断线分别处理。已终结的Attempt永不重开；同一Run与非终结工作可在恢复核验后继续。已完成或明确取消的Run保留终态，后续委托建立后继Run并引用原成果。单纯租约过期或缺少心跳只说明观察失效，不表示所有权可以安全转移。

有外部副作用的动作保存操作标识、对象、意图摘要、执行结果和不确定性。若发生“请求已发但回执未存”，先查目标状态和可用去重记录；不能判断是否执行时只阻塞相关动作并说明所缺证据。不可见于Team控制入口的原生工具、自由shell或远程服务可能无法统一截获；能力探测必须列出覆盖范围。无法保证安全重试的动作不自动重发，也不能把写一条日志当成已经防止重复。

工作笔记负责给继任者指明目标、当前进度、未解决问题与关键来源；输入说明从正式定义和运行记录按需生成。协调者同样通过这些材料恢复，不能成为不可替代的记忆中心。记录用户可读的结论、理由和证据，不以保存模型私有推理作为恢复前提。

## 9. 监督、资源与用户可见性

监督触发来自关键结果、依赖或目标变化、故障、资源接近边界、明确期限以及实测确认的无进展信号。普通消息、工具输出和心跳不各自触发一次全局审查。同类重复事件可以合并，保存已处理游标；新证据到来前避免重复相同模型调用。运行程序发现超时或失联，先提供观察事实，模型再判断业务是否停滞。

调度在派发前预约可判定的执行槽及资源，覆盖协调、执行、协助、修复、审查和内部Subagent。观察额度、token和墙钟分别记录，不互相换算成伪精确成本。缺失遥测时明确unknown，采用当轮约定的保守资源边界；未登记子执行、路由改模或未知消耗使额度保证不成立时，停止受影响的新派发并核实。具体模型与档位使用有效运行约定，当前实验仍为gpt-5.6-luna/max，不能把它写成所有用户的固定模型。

插件的安装本身不等于运行程序已经常驻。运行期间需要有实际启动并可观察的Team控制进程负责事件、队列与恢复；退出、设备睡眠或宿主不可用时不保证继续推进。重启需显式恢复链路。启动方式、进程退出和宿主生命周期是后续实测项目，不能通过文档承诺后台监控。

用户看到目标与本轮交付点、实际执行者及当前责任、待处理协作、等待原因、重要调整、有效成果和剩余未知项。每个重要结论可展开相关可读消息、判定理由、版本及证据。显示最后核对时间，不根据会话数量或消息数量编造完成百分比。普通通知适度合并；需用户判断、影响交付、停止失败或重大方向变化及时呈现。

评价同时记录成果质量、遗漏、返工、真实缺陷、验证耗时、协调调用、排队、恢复开销和用户介入。误拦截应由有依据的复核标注，不能把所有校验失败自动算误拦截；同样不能用调用少或测试绿直接证明团队收益。

## 10. A2A参考及边界

2026-09-14核对官方[任务生命周期说明](https://a2a-protocol.org/latest/topics/life-of-a-task/)与[A2A 1.0.0规范](https://a2a-protocol.org/v1.0.0/specification/)。官方区分轻量Message和有生命周期的Task，终态Task不重开；关联的后续工作可通过上下文与引用延续。规范中的取消是请求，成功需核实；Send Message去重不是一项无需实现即可获得的保证。

本设计借用上述语义，通信仍仅面向Codex，不增加A2A网络服务或其他执行平台。本地Work item高于具体执行尝试；A2A Task语义优先对应一次有明确终态的Attempt。contextId用于相关交互，不与原生threadId或长期projectId强制等同。Message关联正文与引用；Artifact表示输出。责任代次、共享写入、接收有效性、预算和产物版本链由Team自行定义和验证。

本地Attempt的interrupted表示原生执行已被中断且该尝试结束；A2A生命周期说明中的interrupted类别包含可续接的input-required/auth-required，两者不能按同一个词直接映射。等待输入与原生回合已经终结分别保存，具体协议映射仍需依据实际实现核对。

这是一份设计层语义对应，不构成线协议实现、兼容性认证或互操作保证。Team的accepted及结果失效语义不能冒称A2A标准Task状态。旧[任务消息模型](06-task-and-message-model.md)保留其历史profile；新实现时按已核对的规范版本确定序列化，不能直接照搬旧字段名。

## 11. 设计约束与仍需实测的部分

当前采用：总体责任明确但可交接、模型判断与确定性程序分工、渐进计划、统一工作记录、自然语言交流、终态尝试不可重开、接收与完成分离、局部版本切换、持久派发和范围内恢复。

仍需实测：Codex的安全切换边界、停止覆盖、原生创建与派发的去重/关联、非Git现场与项目归属、协调会话替换、进程启动退出、资源可观测性，以及队列策略的质量和成本。能力不足时采用有证据的降级方式并保留unknown；不会把上述设计写成旧里程碑已经验收的能力。第一步实现与检验范围见[验证及迁移计划](26-execution-validation-and-migration.md)。
