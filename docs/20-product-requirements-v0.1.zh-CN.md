## 0. 文档边界与确认状态

本文整理本轮讨论已经确认的产品目标、使用方式、运行要求和长期方向，供后续产品设计、架构选择、开发拆分和验收使用。

本文不对当前仓库、用户本机安装版本或 Codex 最新接口做实现审计。文中的“应当”“必须”“支持”描述目标需求，不代表当前功能已经实现。此前讨论中提及的具体原生接口、模型配置、监控事件及后台行为，需要在目标 Codex 版本、执行界面和实际环境中重新核验。

需求按三类理解：

- **已确认需求**：来自用户明确表达，或用户已接受的整体需求定义。
- **设计建议**：为满足需求提出的结构、字段、流程和验收方法；可在实现前调整。
- **待验证或待决策**：涉及原生能力、具体接口、阈值、存储方式、运行部署和控制层选型，不提前写成事实。

第一阶段的目标是一次完整、可控的自动化团队执行。长期模块负责制是后续演进方向；不能要求用户先拥有一个长期项目，也不能以长期架构研究为由推迟第一阶段的实际交付。

## 1. 产品描述

### 1.1 一句话定义

**Codex Team 是面向 Codex 的可控多会话工程协作系统：把用户的产品或项目意图，转化为经过澄清的目标、可调整的执行团队和可追溯的项目状态，在授权范围内自动推进到用户指定的验收检查点。**

### 1.2 完整产品描述

用户通过 Team Skill 的 Auto 入口描述想开发的产品、想改进的现有项目，或者希望完成的工程目标。Team 通过必要追问厘清用户、场景、功能、设计、现有资产、成本约束、验收方式和允许自主执行的范围，同时生成项目文档与团队执行方案。

Team 根据任务结构和当前可用能力，动态判断哪些工作由当前 Session 完成，哪些交给其内部 Subagent，哪些值得创建独立 Session。独立 Session 可以在自己的 Worktree 中工作，在授权和预算内继续调用 Subagent，并围绕各自目标完成规划、实现、验证和修复。

多个 Session 通过共享项目事实、可追踪的协作请求和集成机制配合。系统提供可视化看板，让用户了解各 Session 正在做什么、相互依赖什么、产生了哪些实际结果、有哪些风险、什么时候需要人工介入。运行中有持续观察、阶段监督、纠偏、失败恢复和会话接替机制，不依赖用户一直盯住所有对话。

用户审阅方案并授权 Run 后，可以不必持续参与日常任务调度。Team 应在预先允许的范围内推进；达到检查点时交付可验证产物并停止，遇到超出授权、预算或可恢复范围的问题时如实暂停，不能自行降低目标后宣布完成。

### 1.3 两个互补层次

**最小执行结构：** 多个独立 Session，各自具有上下文、执行历史和代码工作区，并能在内部使用 Subagent；Team 负责协调、集成和监督。

**长期演进方向：** 产品模块、责任、契约和项目记忆持续存在，Session 可以创建、拆分、合并或替换。组织的连续性由共享事实保障，不由某个永远不关闭的 Session 保障。

两者不互相替代。前者是可实施的基础，后者决定系统在持续开发中的扩展方式。

## 2. 目标用户与核心使用场景

### 2.1 首要用户

首要用户是使用 Codex 推进产品或工程项目的个人开发者、项目负责人及小型团队。他们愿意定义目标和关键取舍，但不希望持续手工拆任务、转发消息、追问进度和处理所有分支交接。

用户可以没有大型项目管理经验，也可以没有长期项目经历。产品必须帮助用户建立足够的目标、边界和验收标准，不能要求用户先学会多 Agent 编排才能使用 Auto 模式。

研究、复现和分享 Codex 多会话工程方法，也是本项目的有效使用场景。本文采用产品需求表达，不因此强加商业化、融资、收入或市场规模目标。

### 2.2 首阶段核心场景

从一个新产品想法、现有代码库的改进目标或明确工程任务出发，经过需求澄清和授权，自动推进到一个有实际产物的检查点，例如：设计方案可评审、核心链路可运行、跨模块功能验收完成、发布候选准备完成。

检查点不必都是“代码完成”。研究结论、设计产物、技术原型、迁移方案、测试报告等也可以成为交付物，但必须定义对应的验收依据。

### 2.3 后续场景

在同一个项目中连续推进多个版本，保留模块责任和设计依据，处理需求变化、接口升级、跨模块改造、负责人替换、运行中断和历史版本追溯。

## 3. 要解决的问题与待证明的价值

### 3.1 用户已经明确表达的问题

1. **执行边界难判断。** 单个 Session 加 Subagent 已经很强，不知道何时值得增加独立 Session；机械拆分可能更贵、更慢。
2. **顶层会话仍可能成为瓶颈。** 增加 Worker 后，若所有理解、汇总和决策仍回到一个主 Session，压力只是向上集中。
3. **项目事实分散。** 目标、方案、历史、进度和失败原因散落在对话、文件和分支中，其他 Session 不容易获得正确背景。
4. **协作需要人工协调。** A 需要 B 帮助时，缺少可追踪的请求、优先级、依赖和处理结果。
5. **长时间执行缺乏可见性和纠偏。** 用户无法仅凭“正在运行”判断是否有进展，也难以同时监督多个 Session。
6. **会话替换可能不断丢失信息。** 连续依赖上一代摘要，担心形成累积损失。
7. **自动化边界不清楚。** 希望授权后推进到检查点，又不希望系统擅自扩展范围、消费资源或进行不可逆操作。
8. **缺少适合个人起步的验证与展示方式。** 第一阶段需要能用于真实项目并展示完整流程，不应只能服务长期运营项目。

### 3.2 产品价值假设

Team 预期通过有选择的并行、上下文隔离、明确责任、共享事实、独立检查和失败恢复，提高工程推进的速度、质量或可控性，并减少用户协调负担。

这些是需要实验验证的价值，不预先宣称多 Session 一定优于单 Session，也不把并发数、任务数、消息数、文档数量作为价值证明。

### 3.3 正确的比较对象

主要基线应是：**一个独立 Codex Session，允许合理使用 Subagent，拥有相同目标、工具、代码起点和可比资源条件。**

另一组对照是用户手工管理多个 Session 和 Worktree，用来区分“多会话原生能力的收益”与“Team 协议、调度和监督的额外收益”。

## 4. 目标、非目标与产品原则

### 4.1 核心目标

- 将产品意图转化为明确、可执行、可验收的工程计划。
- 动态选择执行层级，以最小但足够的团队推进工作。
- 支持多个独立 Session 各自完成具有局部自主性的工作。
- 让项目事实可共享、可查询、可恢复，并减少重复说明。
- 让协作、依赖、进展、成本和风险对用户可见。
- 在用户无需持续盯守的情况下，发现偏离并在授权内纠正。
- 支持中断恢复和必要的 Session 交接，保留失败历史与有效成果。
- 在明确检查点收口，以实际产物和证据说明达成情况。

### 4.2 非目标和默认限制

- 不要求所有任务都组队，也不要求每个模块、角色或工作流单开 Session。
- 不以模仿公司职位和层级数量作为产品目标。
- 不承诺完全消除模型错误、信息损失或用户决策。
- 不承诺所有项目都提速、省 Token 或提高质量。
- 不默认自动推送、生产发布、支付、删除数据、覆盖用户改动或执行其他高风险外部操作。
- 不重新实现 Codex 的模型推理、工具执行、底层会话存储和完整开发环境，除非后续有明确必要性与范围决策。
- 当前需求围绕 Codex；通用跨平台 Agent 协议和对所有编码工具的支持不属于已确认范围。
- 第一阶段不以无限期后台运行、成熟商业平台或多年项目管理能力为前提。

### 4.3 产品原则

**目标优先，组织可变。** 用户确定交付目标，Team 决定并调整组织方式。

**单个 Session 能完成，不等于一定该拆或一定不该拆。** 需要比较实际并行收益、质量收益和协调代价。

**项目事实共享，执行上下文按需加载。** 不把全部项目历史塞给每个 Agent。

**职责可以分层，事实不靠逐层转述。** 使用层级时，保留对原始需求和证据的直接访问。

**允许局部自主，限制隐性扩权。** Worker 可以规划和请求资源，不能自行扩大预算、产品目标或风险权限。

**状态必须能追到依据。** 自述完成、自动测试通过、独立审查通过和用户认可分别记录。

**失败保留，恢复追加。** 后继成功不覆盖此前失败，也不制造无关产物来满足流程形式。

## 5. 第一阶段的完整用户旅程

以下入口名称为目标交互示意，不代表当前已支持的实际命令。

```text
选择 Team Skill 的 Auto 模式
→ 描述产品 / 项目目标
→ 有针对性地追问和澄清
→ 形成项目文档与 Team 方案
→ 用户查看目标、分工、权限和检查点
→ 用户授权 Run
→ 检查环境并启动执行
→ 动态分配、协作、监控、纠偏和集成
→ 达到检查点，或者因明确原因暂停
→ 交付产物、证据、剩余问题及可继续的位置
```

### 5.1 输入

支持新项目与已有项目。输入可以包含自然语言目标、仓库、设计资产、需求文档、参考产品、运行环境和既有约束；不能只接受预先写好的完整技术规格。

### 5.2 澄清

系统根据缺失信息追问：目标用户、实际问题、关键使用场景、产品形态、功能边界、设计要求、现有资产、时间或成本约束、验收依据、目标检查点以及风险授权。

客户、商业模式、运营等问题按项目需要询问，不把所有项目强行当作商业 SaaS。已回答的信息不能反复追问；无法确认的信息应标成假设、待决定或阻塞项。

### 5.3 方案与文档

形成两组相互关联的结果：

- **项目方案：** 做什么、为谁做、什么不做、主要设计、实现阶段和如何验收。
- **团队方案：** 谁负责什么、为什么这样分、使用什么执行资源、如何协作、权限和预算是什么、何时停止。

用户不必阅读全部底层日志，但应能查看影响目标、成本和风险的关键决定。

### 5.4 Run 授权

Run 前明确当前检查点、可自主执行的操作、不可越过的边界、可能消耗的资源和需要用户再次决策的情况。授权应绑定到可追溯的方案版本。

需求澄清和方案生成本身不自动授权创建大量会话、执行破坏性操作或持续消耗无上限资源。

### 5.5 执行与收口

运行中不要求用户持续手工转发消息。到达检查点时，应根据预先定义的标准验证产物，报告已完成、未完成、未验证、被外部条件阻塞的部分，并停止继续扩展范围。

遇到不可自行解决的情况时，保存当前现场和下一步，使用户能明确选择继续、修改范围、补充条件或结束。

## 6. 需求、工作、执行资源之间的关系

### 6.1 不应绑定为同一个对象

- **项目 / 产品**定义整体目标。
- **需求**描述用户需要获得的行为或结果。
- **模块**是产品中相对持续的责任边界，不一定对应一个目录。
- **工作包**是一段有目标、范围和验收条件的工作，可以跨多个需求，也可能只是某个需求的一部分。
- **工作流**描述完成工作的过程，不自动决定 Session 数量。
- **Session**是承担工作的执行载体，可以先后处理多个工作包，也可以被替换。
- **Subagent**用于 Session 内部的委托；具体能做什么、持续多久、如何配置取决于实际原生能力。
- **Worktree**用于隔离代码现场；它不是完整项目记忆，也不是业务模块身份。
- **检查点**定义本轮运行到何处停止、以什么证明。

### 6.2 分配方式

一个 Session 可以承担多条相关工作流。一个复杂模块也可以由多个 Session 协作。只读调查、验证和设计工作不应被迫生成无意义的代码提交或独立写入工作区。

工作包、模块、Session 和 Worktree 之间的关系必须明确，但不必固定一对一。

### 6.3 局部自主性

主协调职责向 Worker 提供目标、输入、边界、接口、验收和升级条件。Worker 在范围内自行制定具体步骤、调用允许的 Subagent、实现、验证和修复。

不要求顶层会话预先写出每一个文件和函数的操作步骤；必要的路径所有权与禁区仍需要明确。

## 7. 动态 Session 分配

### 7.1 已确认需求

优先采用模型参与判断的动态分配，而非固定角色表或“一个工作流一个 Session”。系统必须能选择少开会话、不开新会话，也能在证据充分时增加、拆分、调整或替换执行单元。

模型能力增强后，分配机制应重新适应当前条件，不把某个项目规模永久判定为必须组队。

### 7.2 判断依据

应考虑工作量和持续性、相关上下文、依赖关系、共享文件与环境、独立验收能力、预计并行收益、启动与沟通成本、集成风险、可用额度以及当前运行反馈。

“它是一条工作流”“文件很多”“模型说很复杂”“上下文已经压缩”都不能单独作为必须拆分或替换的充分理由。

### 7.3 建议的决策过程

模型提出分工及理由，确定性规则检查权限、资源、路径冲突和预算，运行证据用于后续调整。初始团队尽量小，但不得为了少开会话而把全部工作重新挤回顶层。

Worker 可以提出拆分、请求协助、升级模型或合并工作的申请。是否允许直接创建顶层 Session，由统一策略决定；无论谁创建，都必须登记并计入全局资源。

### 7.4 全局约束

同时约束独立 Session 与各自 Subagent 的总量、并发、预算和权限，避免“每个 Session 都没有超限，但全项目资源失控”。

分工变化可以在授权内自动进行；改变产品目标、检查点、主要风险或突破资源上限必须按策略重新获得确认。

### 7.5 验收重点

给一个小任务时，应能保持单 Session 或内部委托；出现确实可独立推进的大工作包时，应能给出拆分依据。不能把会话数量增加本身记为进展。

## 8. 模型、Subagent 与通信配置

### 8.1 必须覆盖的配置内容

独立 Session 的模型与思考程度、Subagent 是否允许及相应配置、并发与预算、升级和降级规则、检查点、可执行操作范围、通信可读性与审计要求。

配置应以当前执行环境实际支持的选项为准。用户请求值、实际生效值和无法观测的状态必须分开记录，不能从提示词推断底层已经使用某个模型。

### 8.2 建议的配置层级

**Auto：** 用户说明质量、速度、成本倾向及必要限制，系统推荐具体配置。对重要资源与风险选择仍需呈现给用户。

**策略预设：** 可以提供节省成本、均衡、质量优先等策略；预设名称和具体实现待设计。

**高级覆盖：** 用户可按 Session 或角色指定模型、思考程度、Subagent 策略、并发量和阶段停止规则。

以上为交互建议，不能据此删除用户明确要求的配置能力。

### 8.3 通信要求

用户关心通信效率和人类可理解性。建议默认采用紧凑的结构化消息加简短可读说明，以共享文档、任务、Commit 和证据引用减少重复背景。

不把只有当时两个 Agent 能理解的临时编码或自然语言摘要作为唯一权威记录。进一步的压缩通信模式可以实验，但必须验证正确率、接收方理解成本、延迟和审计能力，不能只看发送 Token 是否减少。

## 9. 共享项目文档与事实系统

### 9.1 已确认需求

每个获授权的 Agent 都能访问与职责相关的项目情况，包括介绍、需求、设计、规划、历史和运行状态。新会话能够据此恢复，不依赖某个旧会话持续在线或人工口述。

“文档系统”是用户当前对这一能力的表达，不预先限定只能使用 Markdown 文件，也不强制立即开发数据库服务。

### 9.2 建议保留的六类内容

1. **目标与验收：** 用户问题、范围、非目标、约束、检查点及其变更。
2. **设计与约定：** 架构、模块、接口、数据结构、视觉和内容规范。
3. **计划与责任：** 工作包、依赖、优先级、负责人、工作区、资源策略。
4. **当前状态：** 实際进展、阻塞、待处理请求、已接受产物、下一步。
5. **历史与决策：** 为什么这样做、哪些选项被放弃、哪些要求已被替代、失败与恢复过程。
6. **证据与索引：** 代码版本、测试、截图、构建、审查、原始材料和必要日志的位置。

### 9.3 内容质量要求

区分已确认事实、合理假设、建议、待验证事项和过期信息。规范和决策有状态与版本；草案不自动成为所有会话必须遵循的新规则。

不把原始对话无限堆积视作项目记忆完成。会影响后续工作的决定必须转化为可引用记录，重要原始材料保留索引供核对。

### 9.4 读取与更新要求

每个会话先获取与当前工作相关的材料、最近变化和继续检索的入口，不默认读取全部历史。资料必须标识适用版本，避免 Worker 在旧契约上继续实现。

全局规范、接口和目标变更要通知受影响责任方；通知应指向原始变更，不经多层转述变成新的口头规则。

多个 Session 不应争抢修改同一份全局状态。可采用独立事件汇入统一视图、指定状态写入者或其他并发控制方式；具体实现待决策。

### 9.5 需求追踪

全局需求必须能关联到负责范围、产物和验收依据，防止拆分后出现“每个局部都完成，但某条整体需求无人负责”。

---

## 10. 协调机制与协作看板

### 10.1 已确认需求

A Session 能向 B Session 或某个能力领域提出协作请求；请求有可见状态和负责人。系统根据依赖、优先级、对方状态和资源条件安排处理，而非依赖用户手动转发 Prompt。

用户有看板观察团队，并能够调整目标内的优先级、暂停、查看风险与证据，以及在必要处作决定。

### 10.2 看板应回答的问题

- 当前产品目标、运行阶段和下一个检查点是什么？
- 谁在做什么、为什么由它负责、使用哪个工作区？
- 最近产生了什么可验证结果，下一步是什么？
- 哪些工作在等待，等待什么、由谁解除？
- 哪些协作请求尚未响应或处理？
- 哪些任务可能偏离、超预算或长期没有有效进展？
- 哪些产物仅由 Worker 声称完成，哪些已验证、已集成或已获用户认可？
- 当前能观测到的资源消耗是多少，哪些值未知？
- 用户现在需要决定什么，暂停后从哪里继续？

不能只显示活跃会话数和消息流。没有可靠依据时，不显示伪精确进度百分比、实际模型、Token 成本或“正常工作”的判断。

### 10.3 协作请求建议内容

请求方、目标模块或能力、问题和背景、相关需求与契约、期待的答复或产物、是否阻塞、期望处理顺序、当前状态、处理负责人和结果引用。

同一个请求的重试不能创建多个重复工作。需要有接收、处理中、等待补充、完成、拒绝或取消等清楚状态。

### 10.4 调度行为

空闲目标可领取请求；繁忙目标按策略排队或在检查点接入；紧急冲突可以触发有限打断；无人负责时可以重新分配或申请新 Session；超出目标或权限时请求用户决策。

允许范围内的直接会话协作，但影响目标、接口、依赖和交付的关键结果必须回写共享状态，不能仅停留在私下消息里。

---

## 11. 避免顶层 Session 成为新的瓶颈

### 11.1 已确认需求

不能让整个团队永久依赖一个承担全部记忆、推理、消息转发和任务监控的主 Session。主协调执行者也需要可替换，项目仍可从共享事实继续。

### 11.2 建议的职责拆分

**运行管理职责：** 保存状态、登记会话、检查依赖、投递任务、更新看板、记录资源和触发检查。

**语义协调职责：** 理解目标冲突、复杂优先级、接口争议、重大重规划和用户取舍。

**监督与验收职责：** 对照目标检查实际产物、偏离风险和交付证据。

这些是逻辑职责，不表示每一项都必须创建常驻 Session。可机械判断的工作不应要求模型反复阅读全文；需要复杂理解时再调用具备必要上下文的会话。

### 11.3 层级组织的使用边界

可以按产品规模形成局部负责人或树状分工，但不预设“像大公司一样层层汇报”就是正确架构。每层传递目标、责任、状态和引用；获授权的接收方仍能直接核对原始来源。

---

## 12. 监控、监督与跑偏纠正

### 12.1 已确认需求

系统必须有“监工”能力：发现工作偏离目标、无效循环、接口冲突、长期没有实质进展或验收遗漏，并能在授权内将执行拉回正轨。

它不能只在所有任务结束后才检查，也不能完全依赖 Worker 自我评价。

### 12.2 建议的三层检查

**机械边界：** 工作路径、禁区、命令权限、资源上限、必要验证是否执行。

**运行迹象：** 计划和 Diff 的变化、重复失败、协作阻塞、最近有效产物、预算和状态新鲜度。

**目标一致性：** 实际功能、用户链路、设计和内容是否满足要求；局部测试通过是否掩盖整体未完成。

上下文压缩、长时间运行和暂时无消息只应作为风险信号，不自动等同于能力衰减、卡死或失败。

### 12.3 建议触发点

开始实现前核对 Worker 理解；第一个可运行结果形成后；计划或接口发生实质变化时；出现反复失败或无有效进展时；集成前后；用户指定检查点前。

检查频率、判断阈值和资源预算通过实验调整，不设伪精确通用常数。

### 12.4 纠偏动作

从补充明确反馈、要求重新说明计划、缩小当前工作范围开始，必要时暂停相关执行、保留现场、限定修复范围、重新分配或交给新 Session。影响产品取舍或超出授权时才升级给用户。

不得为了恢复执行而静默修改需求、放宽验收、删除失败记录或覆盖用户未提交改动。

### 12.5 非代码质量

界面审美、文章解释质量、交互流畅度等要求需要参考样例、实际运行产物和合适的独立或人工评审。自动测试通过不能替代这些验收。

需要用户判断的检查点应提前说明，不能在 Run 后临时把主观质量目标取消。

---

## 13. 验证、集成与检查点

### 13.1 验收链

每个工作包明确输入、目标和结果标准；模块产物经过局部验证后交接；集成后检查跨模块真实链路；独立审查核对重要遗漏；检查点依据全部必要条件决定是否达成。

测试由执行者编写并通过，不自动等于独立验收通过。不同验收层的结论必须保留边界。

### 13.2 证据绑定

证据应绑定适用的代码或产物版本、工作环境和执行条件。不能用旧版本测试证明新版本已通过，也不能只看外层脚本退出码而忽略验证实际未执行。

复用证据时说明仍然有效的范围；修改触及原结论时补测，不机械全量重跑，也不无依据跳过。

### 13.3 集成

写入与合并有明确所有权和顺序，跨模块契约变化可追溯。不能让所有 Worker 同时接管同一个集成现场。

集成可以在阶段内持续发生，不必等所有大分支完成后一次性合并；具体节奏由依赖和风险决定。

### 13.4 检查点定义

每个检查点至少回答：应交付什么、以什么证明、哪些必须人工确认、哪些条件缺失会阻塞、到达后停止还是进入已授权下一阶段。

建议状态包括：未开始、执行中、待验证、待用户确认、已达成、因明确条件暂停。名称可以调整，但不得把“测试通过”“代码可交付”“线上验证通过”混成一个完成状态。

### 13.5 用户否决与需求变化

用户否决产物或改变标准时，保留旧结论在旧标准下的适用范围，建立新的需求版本和后续工作。不得抹掉历史，或继续用旧审批支持新目标的完成声明。

---

## 14. 中断、失败恢复与 Session Handoff

### 14.1 已确认需求

持续迭代中，Session 可以被更新和替换；交接不能主要依靠一代代摘要的重复压缩。失败和中断后应尽量保留已验证成果，不让整个项目无条件重来。

### 14.2 新 Session 的恢复来源

当前代码和产物、有效需求、最新已接受设计与契约、明确的任务状态、决策记录、验证证据、未完成工作和可检索原始材料。

旧 Session 的交接摘要是导航和增量说明，不是唯一事实源。原始记录可以按需要检索，不要求把全部对话重新注入。

### 14.3 交接包建议内容

当前职责、工作区与版本、已完成和未完成需求、关键决策位置、有效证据、已知失败与风险、待处理协作、下一步动作，以及不应无意义重复的工作。

### 14.4 接管验证

新 Session 先核对当前状态、接口、环境、产物和下一步，暴露不确定性后再取得责任。原负责人退出和新负责人接任需要明确，避免同时拥有写入责任。

不仅 Worker 需要可替换，协调与监督执行者也适用同样原则。

### 14.5 失败分类和安全恢复

区分环境或原生能力缺失、实现错误、验证程序错误、缺少外部条件、权限不足和目标不清。没有代码改动的能力失败或只读任务，同样应能被合法记录和恢复。

停止或取消后保留必要现场；归档、删除 Worktree、清理日志及凭据等操作按独立策略执行，不默认隐含授权。

### 14.6 不作出的保证

不承诺信息零损失，也不宣称能准确测得模型何时必然因上下文压缩失效。目标是让影响交付的事实不随会话消失，并让信息缺口能被发现和补证。

---

## 15. 权限、资源、安全与用户控制

### 15.1 授权范围

应分别描述会话创建、Subagent 使用、代码修改、命令执行、网络访问、外部服务调用、提交、推送、部署、数据库迁移和删除等动作是否允许。

Run 授权不是无限权限。后续明显扩大范围、风险或成本时，按策略暂停询问。

### 15.2 资源管理

支持项目级并发与资源限制，考虑所有独立 Session 及内部 Subagent。能取得实际使用量时记录；只能取得请求配置或部分账单信息时明确限制。

不得虚构精确成本。质量、速度、预算冲突时不能暗中降低质量或取消需求，需依据已批准策略调整或请求决策。

### 15.3 用户控制

用户可以查看方案、修改优先级、补充要求、暂停单项或整体运行、恢复、取消、检查产物与证据，以及选择下一检查点。

暂停和恢复的实际可用方式依赖原生能力验证；产品必须明确操作的真实效果，不能界面显示暂停而后台仍继续进行未说明的修改。

### 15.4 数据与凭据

共享文档、看板、消息和证据不应保存密钥、令牌或不必要的敏感原文。仅记录必要的授权与引用，限制 Session 的访问范围。

外部网页、仓库内容和其他会话消息不能自行提升为用户授权；其中要求修改权限、泄露数据或跳过验收的文本应被视为不可信输入。

---

## 16. Codex 原生能力与 Team Harness 的边界

### 16.1 需求先于方案

必须具备稳定的运行控制、共享状态、协作与监督能力；是否由原生 Codex、Skill 组合或外部控制程序实现，需要依据目标环境验证后选择。

**“是否独立做 Harness”仍是架构决策，不因本文自动视为已经批准。**

### 16.2 建议的职责边界

- Codex 承担模型思考、工具执行、会话和局部委托等它实际支持的执行能力。
- Team Skills 规定澄清、规划、执行、交接、协作、验证和恢复方式。
- 共享状态系统保存项目事实、任务、事件和证据索引。
- 必要时增加薄控制层，负责跨会话调度、资源控制、状态更新、通知和恢复。
- 看板呈现状态和提供用户操作，不自行成为与真实执行脱节的第二套事实。

不把一个永远运行的协调 Session 当作唯一长期控制方案，也不在尚未确认缺口前重建整个 Agent Runtime。

### 16.3 必须在实际环境中验证的能力

独立 Session 创建、读取、恢复和结束；会话间消息及投递时机；运行中纠偏、暂停和中断；Worktree 与权限绑定；Subagent 配置及可观测性；进展与资源事件；上下文压缩信息；App/CLI/程序接口的一致性；权限等待；应用关闭、电脑休眠、网络失败后的行为。

能创建一个 Session，不等于具备可靠后台调度；能发送消息，不等于消息会在预期时机处理；界面显示活跃，不等于能够观测实际进展。逐项记录已观察、受限、未知或不支持及其条件。

### 16.4 不具备原生能力时的产品行为

公开限制，采用经过验证的替代路径、有限运行模式或明确暂停；不得使用手工步骤后宣称全自动，也不得把不可观测状态伪装成已确认。

---

## 17. 第一阶段与长期路线

### 17.1 第一阶段最终形态：到检查点的可控自动执行

必须打通：Auto 澄清、项目与 Team 方案、Run 授权、可调整的会话分配、内部 Subagent 政策、共享项目状态、协作请求、可视化进展、监督纠偏、基本中断恢复、集成验收及检查点收口。

这是一条完整用户链路，不是只验证“可以启动多个 Session”。第一阶段可以限制在明确支持的环境、有限预算和有边界的检查点内，不需要承诺无限期无人值守。

应具备必要的交接记录和新会话恢复路径，但无需首先完成全自动的长期人员轮换系统。架构中必须避免把模块身份永久绑定到一次 Session。

### 17.2 第二阶段：持续迭代与稳健调度

支持同一项目跨多个检查点持续推进，处理需求版本、接口变化、有效证据复用、自动或半自动接替、协调执行者替换和更完整的中断恢复。

### 17.3 长期方向：可调整的模块团队

模块、责任、契约和项目记忆长期存在。系统能根据工作和模型能力调整责任边界、组织规模和协作方式，而不是固定模拟一家公司。

长期目标必须以第一阶段真实运行问题为输入，不能先堆叠大量尚无价值证据的角色和管理层。

---

## 18. 评测、练手项目与宣传展示

### 18.1 不要求只有长期项目

第一阶段可以在一个新项目或现有项目的明确检查点上验证。用户无需先积累长期项目经验。

建议逐步形成：真实项目验证整体交付；同一项目的连续变化验证延续性；独立保留的任务验证泛化；不适合并行的负例验证收缩能力。

### 18.2 项目选择维度

比较任务的持续性、可并行部分、接口耦合、共享写入、验证难度、环境成本、外部依赖和用户实际判断能力。项目大小、行业标签和代码行数不能单独决定适配性。

### 18.3 建议实验场景

小任务不必组队；多条独立深工作并行；共享接口变化；高耦合工作需要串行；Worker 偏离；一方需要另一方协助；会话或运行中断；更换负责人；测试通过但用户链路失败；达到检查点主动停止。

用于改进系统的训练案例与用于证明收益的未见案例分开。一个已反复调试的项目不能独自证明普遍优势。

### 18.4 三类独立结果

**产品结果：** 功能、设计或其他产物是否达到约定。

**系统运行结果：** 状态、协作、权限、监督、交接和验收是否按预期工作，有多少人工兜底。

**对照结果：** 与单 Session 加 Subagent、人工多 Session 相比，质量、时间、资源和人工负担是否改善。

产品成功但流程依赖手工绕过，不能称为全链自动成功；流程合规但产品未达标，同样不能称为交付成功。

### 18.5 核心指标建议

检查点达成率、重要需求遗漏、真实缺陷、用户干预次数及耗时、总执行时间、可取得的资源消耗、协作等待、无效重复工作、偏离发现与恢复情况、交接后继续工作的质量、状态与实际产物一致程度。

对照控制代码起点、需求、工具、环境和可比模型策略。分别做同预算比较与允许额外资源的提速比较，避免把额外开销隐藏在“更快”之后。无法观测的指标如实留空，不推测填充。

### 18.6 展示方式

展示从 Brief 到检查点的完整过程：初始目标、为什么这样分工、看板真实进展、一次有意义的跨会话协作、一次偏离或失败处理、最终产物与验证、用户实际介入。

宣传重点是可控自动化和可追踪交付。不能把动画看板、会话数量或一句话生成演示本身当成团队价值，也不预先承诺比单 Session 快若干倍。

## 20. 第一阶段关键验收情景

以下为建议验收情景，不代表已完成测试；具体测试数据与通过阈值在开发前冻结。

| 情景 | 应出现的行为 | 不可接受的行为 |
|---|---|---|
| 用户只给一个产品想法 | 追问关键缺口，形成明确目标与检查点 | 直接假设全部需求并开始大规模编码 |
| 用户提交很小任务 | 可以不创建独立 Worker Session | 为满足 Team 形式机械创建多个会话 |
| 多条工作可独立推进 | 说明分工依据，隔离代码现场并并行交付 | 并发写共享文件且无人负责冲突 |
| 工作中发现需要拆分 | 提交或生成可解释调整，核对预算和依赖 | 无限递归创建执行者 |
| A 需要 B 协助 | 请求可追踪，明确接收方和处理结果 | 用户被迫充当消息中转站 |
| 全局要求被局部拆分 | 仍有负责人和整体验收依据 | 各模块都完成但整体要求无人处理 |
| Worker 修改方向偏离 | 在关键检查点发现，给出证据并纠偏 | 只等最后用户发现，或自动改写目标 |
| 进展无法观测 | 标明未知或状态过期，采取安全检查 | 单凭活跃状态显示正常推进 |
| 自动测试通过但体验失败 | 保留产品层验证并判定未达标 | 用测试数量代替用户目标 |
| 运行或 Session 中断 | 保存现场，识别有效产物与下一步 | 重做全部工作或静默丢失改动 |
| 新 Session 接任 | 读取原始事实并核对当前状态后继续 | 只读上一代摘要就声称接管成功 |
| 外部条件缺失 | 明确阻塞对象与已有产物的交付边界 | 无证据宣布外部功能已验证 |
| 达到授权检查点 | 交付结果与证据，停止扩展工作 | 自动开始未授权下一阶段 |
| 用户修改目标或否决结果 | 记录新版本与影响，重新规划相关工作 | 删除旧结论或用旧标准继续宣布完成 |

## 21. 非功能要求与主要风险

### 21.1 非功能要求

**可观测性：** 关键状态有来源、时间和适用范围；状态停止更新能被识别。

**可恢复性：** 部分失败不应让所有已接受工作失效；恢复动作本身可追溯。

**一致性：** 不重复领取同一任务，不出现未声明的双重写入所有权，不把互相冲突的方案同时当作生效规范。

**可审计性：** 目标变化、资源调整、授权、人工介入、失败、替代方案和最终验收都可追踪。

**成本透明：** 区分协调、实现、验证、返工及外部服务开销；无法取得的部分明确未知。

**可用性：** 普通用户不必理解全部 Agent 配置就能开始，高级用户又能精确覆盖关键策略。

**兼容性：** 对 Codex 版本、操作系统和执行界面的能力差异显式处理，不把一次环境测试外推为通用保证。

### 21.2 主要风险

- 过度拆分和通信使多会话比单会话更低效。
- 模型无法可靠判断自身能力或运行风险。
- 顶层协调会话再次积累所有信息。
- 共享文档过量、过期或相互冲突。
- 看板状态由自述驱动，与真实代码和产物脱节。
- 深层分工形成失真转述和责任空缺。
- 日志与状态收集本身影响执行成本或泄露敏感信息。
- 验收只关注机器可测项，漏掉真实用户目标。
- 原生能力、权限、版本或运行环境不足以支持产品承诺。
- 连续在同一案例调优，产生只对特定任务有效的机制。

每项风险均应对应实验、监控或明确降级路径，而非仅增加一条提示词。

## 22. 待决策事项

这些事项不妨碍本文作为需求基线，但会影响实现方案。

1. 第一阶段支持的 Codex 执行界面、版本和操作系统。
2. 原生能力能覆盖到哪一步，哪些缺口需要薄 Harness；是否启动外部控制程序的开发。
3. 共享状态先用文件、数据库还是混合方式；并发写入、检索和版本机制。
4. 看板放在哪里，怎样与用户授权和实际运行保持一致。
5. 动态分配使用哪些信号，如何设置并发、预算、监督频率和升级阈值。
6. 模型与 Subagent 配置的实际支持范围，生效状态与资源数据怎样核验。
7. 会话暂停、消息处理、自动继续及电脑休眠等情况下的真实边界。
8. Handoff 接管测试、历史保留与清理策略。
9. 用户可读通信和进一步压缩通信的可配置范围。
10. 第一组真实工程案例、负例、保留测试与对照实验资源。

这些应通过小型能力核验与真实执行数据逐步决定，不以预设固定组织结构代替验证。

## 23. 产品完成的判定

第一阶段的完成，不是启动若干 Agent，不是生成一套文档，也不是制作一个能展示任务动画的看板。

**只有当用户能够从产品意图出发，完成必要澄清和授权，让 Team 在共享事实、资源边界和监督机制下组织执行，并在约定检查点获得可验证的产物或明确的暂停结果，第一阶段的产品闭环才成立。**

长期的完成方向，是让这种能力跨需求变化、代码版本和 Session 更替仍保持连续；同时随着模型能力变化，能够扩大，也能够收缩团队，而不丢失产品目标和责任。
