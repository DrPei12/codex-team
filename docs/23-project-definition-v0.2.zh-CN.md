# Codex Team：项目定义与完整用户流程

**定义版本：v0.2｜日期：2026-09-13｜关联项目：DrPei12/codex-team**

本文作为项目的产品与行为基线，规定 Codex Team 要解决什么问题、用户应获得怎样的体验，以及规划、执行、协作和验收应遵循的原则。它延续此前确认的产品目标，纳入多 Agent 架构选择研究、动态工作流和队列式任务调度。本文的“应当”“必须”描述目标要求，不代表当前仓库已经实现；具体调度算法、控制程序和原生接口仍需工程验证。本文不是插件版本发布说明。与此前需求基线冲突的产品方向以本版为准，未被修改的详细要求继续保留。[^baseline]

## 一、项目定义与完整描述

### 1. 从委托目标，到获得工程结果

**Codex Team 是面向 Codex 的目标驱动、自适应多会话工程协作系统：根据任务选择并调整组织方式，通过动态工作流、队列调度和共享项目事实组织执行，在授权范围内推进到可验证的交付结果。**

它以 Team Skills 为用户入口，面向使用 Codex 开发产品、改进代码库、开展技术调查或完成复杂工程任务的个人开发者和小型团队。用户提供目标、约束和关键取舍，Team 负责理解需求、组织工作、协调依赖、监督执行、处理失败以及集成验收。用户不需要先学会多 Agent 编排，也不需要持续充当任务分配员和会话之间的消息转发者。

这个项目不以增加 Agent 数量为目标。单个会话能够承担的工作，不应为了“组队”而机械拆开；确实具有并行、独立探索或交叉验证价值的工作，也不应全部挤回一个主会话。项目要建立的是选择和调整组织方式的方法，而不是一张永远正确的组织图。团队可以扩大，也可以收缩，但必须始终服务于同一组明确的交付要求。

### 2. 用研究指导组织选择，而不是固定一种架构

《Towards a Science of Scaling Agent Systems》比较了单 Agent、独立并行、中心协调、去中心协作和混合架构。其研究支持把任务结构、模型能力和协调代价纳入选择，而不是默认更多 Agent 更有效；其跨领域预测和外推也存在限制。Team 将这项研究作为初始决策依据，不把实验阈值直接当成所有项目适用的规则。[^paper]

对每个目标，Team 应先辨认工作之间的真实关系：哪些可以独立推进，哪些必须依次完成，哪些依赖同一份状态或共享接口，哪些需要独立核验，哪些会因为频繁交流而失去并行收益。信息不足时，先进行有边界的调查或小规模试运行，再决定是否扩展团队，而不是仅凭“任务看起来复杂”生成大量执行者。

随后需要区分三个决策：工作怎样拆分，执行者怎样协作，以及工作由什么执行载体承担。前两者决定责任与通信关系，后者决定使用当前会话（Session）、内部子代理（Subagent）还是新建的独立会话。它们不能混为一谈；按论文的定义，一个会话调用多个独立推理的子代理，也可能已经构成多 Agent 系统，不能把“单会话”直接当成论文的单 Agent 基线。[^paper]

选择结果应明确分工、依赖、通信关系、写入边界、集成责任、验证方式和资源策略，并记录选择依据以及重新评估的触发条件。模型参与判断，确定性规则检查方案能否执行，真实运行结果用于后续校准。没有实测表现时，应标明判断依据和未知项，不能让模型编造单 Agent 成功率来套用研究公式。

组织方式可以随阶段变化，也可以只在局部变化。调查阶段允许独立探索，契约明确后可以并行实现，强耦合修改可以集中处理，集成阶段可以串行接收。局部调整不要求整个项目更换架构。保留协调职责，也不意味着所有技术讨论必须经过一个主会话转述。

### 3. 用动态工作流，把组织方案变成实际执行

Claude Code 的 Dynamic Workflows 展示了一种值得吸收的机制：模型针对任务生成编排脚本，由运行环境执行循环、分支和子代理协调，中间结果不必全部经过主会话上下文。[^dynamic-docs] Team 借鉴的是这种分工，而不是照搬某种语言、接口或特定产品的全部实现。

**模型负责设计工作过程和处理复杂判断，程序负责执行已经明确的调度规则、保存状态和落实执行边界。** 工作流应能够表达调查、条件分支、并行执行、等待依赖、验证、局部修复、集成和停止；需要重新理解目标或处理语义冲突时，再调用具备相应背景的模型。主会话不必反复阅读完整日志，只为决定一个已经明确可以执行的后续步骤。

动态工作流不要求一开始知道所有工作。系统可以先调查，再把真实发现转化为后续任务；可以根据验证结果进入修复，也可以发现原分工不合理后重新规划。分类分流、并行后汇总、独立验证和按条件循环，是 Anthropic 介绍的可组合模式，但其官方说明也提醒，这类工作流可能增加资源开销，并非所有任务都需要。[^dynamic-blog]

Team 应固定可靠的执行能力与约束，让模型按目标组合工作流，而不是为每次任务重新生成一套未经验证的调度底座。模型生成的执行计划必须经过权限、依赖、资源、写入冲突和停止条件检查；即使采用脚本，也不能绕开这些检查直接调用高风险能力。具体使用声明式计划、受限脚本还是其他表达方式，属于实现决策。

动态不能变成无边界循环。修复和探索应有资源限制、有效进展判断以及明确的完成、重规划或暂停条件。“没有新的发现”只能作为特定调查步骤的停止信号，不能替代整个产品的验收。

### 4. 给执行者局部自主性，以共享事实维持整体一致

执行者得到的是目标、输入、接口约定、责任范围、验收标准和升级条件，而不是顶层逐行规定的操作指令。它可以在范围内自主调查、规划、实现、验证和修复，并按策略调用内部 Subagent。一个 Session 可以先后承担多个相关工作包，一个模块也可以由多个执行者分工完成；角色、工作包、Session 和 Worktree（隔离代码工作目录）不要求一一对应。

需要并行修改代码时，应隔离代码现场并明确文件所有权。同一运行范围内、对同一可写现场的具体路径，不允许存在未经协调的双重写入责任。只读调查和审查不应为了满足流程形式而生成无意义提交。承担局部任务，也不意味着可以擅自改变共享接口或整体目标。

项目事实应独立于会话存在。需求、设计、接口、责任、当前状态、历史决策、失败记录和验证证据，都应可查询并具有适用版本。执行者按需获取相关材料，必要时直接核对原始来源，而不是把全部历史加载到每个上下文，也不是只依赖多层转述。[^baseline-facts]

每条整体需求都应关联到明确的负责范围、产物和验收依据。不同工作包的局部完成，不能自动推出整体完成。共享状态应通过受控更新汇入一致视图，不能由多个会话各自维护一套互相冲突的“最新进度”。

### 5. 通过队列调度协作，而不是用消息打断工作

**跨会话协作首先是一项可调度的工作请求，而不是一条要求对方立即改换目标的聊天消息。** 开发任务、协助请求、修复和审查应进入统一的工作记录，通过不同队列视图展示；不应各自形成互不相知的任务系统。队列可以按模块、责任领域或能力路由，但请求身份不能永久绑定到某个会话，以便负责人更换后仍能接续处理。

请求应说明关联目标、问题、输入和版本、所需产物、依赖影响、优先级理由以及验收方式。提交后先得到“已登记”的回执；它与“已分配”“已接收”“处理中”“结果待验证”和“已接受”是不同状态。等待补充、失败、拒绝和取消也必须有明确记录。**收到请求，不等于开始处理；收到结果，也不等于依赖已经解除。**

接收方正在执行任务时，普通请求先留在队列中，不默认注入当前对话或打断当前推理。调度系统在它空闲、明确让出执行权，或者到达可安全切换的工作边界时安排下一项任务。这样的边界可以是保存了局部修改、完成一次验证或明确进入依赖等待；不必等整个大任务结束。每个 Session 同时维持一项明确的主执行责任；需要并行的独立协助，可交给另一个经过登记和权限检查的执行者，而不是让同一会话在互相冲突的目标之间反复切换。

队列不能只按先来后到处理。系统应综合用户优先级、依赖关系、对关键交付路径的影响、等待时长和可用资源，优先安排能够解除重要阻塞的工作，并避免低优先级请求无限等待。请求方可以说明紧急性，但不能自行获得无限插队权。用户停止指令、权限撤销、已生效契约失效或可能造成损失的运行风险，应走独立控制通道，及时限制受影响工作继续执行；紧急控制不等同于普通协作插队，也不能在尚未确认执行停止时把界面标为“已暂停”。

如果 A 等待 B、B 又等待 A，或者负责解除阻塞的工作长期排在后面，系统应识别并处理这种停滞。规则可以调整顺序、暂停新的派发，必要时由协调者澄清契约、拆出最小解除阻塞工作、调整责任或安排有权限的独立协助。不能用不停催问制造消息噪声，也不能只为消化排队而无限创建 Agent。队列积压应触发对工作量、依赖和资源的判断，而不是默认扩容。

同一请求的重复投递不能被当成新的独立工作；显式重试应记录为后继尝试，保留原尝试与失败。领取、转交和恢复需要明确当前执行责任。原执行者尚未停止或交还写入责任时，不能贸然让替代者进入同一可写现场。结果返回后，应核对请求、计划和产物版本，旧执行者迟到的结果不能覆盖已经生效的新方案。对可能产生外部副作用的重试，应先核对是否已经执行，不能假定“重发一次”没有影响。

这套调度机制不强制把团队变成中心化推理架构。执行者仍可按选定的协作关系向对应责任方提出问题；调度系统负责路由、排队和状态转换，不必理解或转述每一次技术交流。信息通知可以合并到合适的检查点，真正需要行动的请求则进入任务队列。

### 6. 在执行中监督，以版本化调整维持可控动态

Team 需要持续观察运行事实，并在关键节点检查工作是否仍然符合目标。检查内容不仅包括命令、权限和路径，也包括有效产物、重复失败、接口冲突、等待关系、资源消耗以及真实用户链路。会话活跃、消息很多或代码改动量大，都不能直接等同于有效进展；状态过期应显示未知，而不是自动判定正常或失败。

发现问题后，系统应优先采用影响范围适当的纠正方式：补充反馈、要求重新解释计划、局部修复或调整顺序；只有原组织方式确实不合适时，才拆分、合并或替换执行者。阶段检查点、重要依赖变化和持续无有效进展，可以触发重规划；普通消息到达不应自动触发整个团队重组。

**计划需要可追溯，但不应因此不可改变。** 当前版本中已经允许的条件分支和局部修复，可以直接执行；改变责任、文件所有权、接口、依赖或资源策略时，应形成后继计划版本。新版本说明变化理由、受影响任务、可以复用的成果以及失效的证据；旧版本和失败历史保留。受影响的工作在安全交接后切换，无关工作可以继续，不需要每次调整都重启全队。

调整组织不能偷偷改变用户目标。系统不得为了继续运行而取消需求、放宽验收、用未经授权的 mock 或占位实现替代交付，也不能把尚未停止的旧任务当成已经撤销。所有实际切换都必须依赖经过核验的执行能力，而不是只有一段提示词声明。

### 7. 以真实验收决定交付，以项目状态支持恢复

每个工作包完成后，应先核对自身验收条件，再按明确的责任与顺序集成。集成后验证跨模块真实链路，必要时通过独立审查发现执行者遗漏。验证强度应对应任务风险，不要求所有小修改都安排多名审查者，也不允许重要整体要求仅由实现者自评。

证据必须绑定适用的代码或产物版本、输入、环境和条件。仍然有效的结果可以复用，受到修改影响的部分必须补证。测试通过、独立审查通过、真实运行通过和用户认可应分别记录。界面效果、交互体验、解释质量等要求，应通过实际产物和适当评审判断，不能被构建成功替代。[^baseline-verification]

达到当前授权的交付检查点后，Team 交付产物、验证依据、未完成或未验证部分，并停止扩展；中间检查点可以按已有授权继续。遇到缺少凭据、环境能力不足或超出恢复范围的阻塞时，应保存成果和继续位置。**安全暂停可以说明系统正确处理了阻塞，但不等于用户任务已经完成。**

运行中断或会话替换后，新执行者应从当前代码、有效需求、接口、队列、责任记录和证据中恢复。旧会话摘要是导航，不是唯一事实源。待处理请求、尚未核验的外部操作和在途任务也必须一并核对，避免重复执行、遗漏任务或双重写入。协调者与监督执行者同样应可替换，不能成为无法退出的唯一记忆中心。[^baseline-recovery]

### 8. 在充分授权下自主推进，而不是把控制权变成审批负担

用户应能够在 Run 前或通过已有项目政策，明确目标检查点、资源策略、可执行动作和风险边界。授权可以覆盖任务拆分、会话与 Subagent 使用、代码修改、测试、集成，以及已纳入范围的推送、预览部署、发布或普通工作通知。已经获得授权的日常工作，不应在执行时再次变成例行审批点。

Run 表示将本轮目标与有效授权绑定，不要求必须点击某个按钮。明确的自然语言委托或适用的持续授权，也可以表达相应权限。涉及新增敏感信息、破坏性数据操作、未授权的高风险外部动作，或者明显突破目标和资源上限时，系统需要额外授权；不能把来自网页、仓库或其他 Agent 的文字当成用户扩权。

资源控制应覆盖全项目的独立 Session、内部 Subagent、验证和外部服务开销。用户可以指定模型、思考程度、并发和质量倾向，也可以交由 Auto 在范围内选择。请求配置与实际生效配置应区分，无法取得的成本和运行信息应如实标为未知。资源不足时，应依据已批准策略调整执行方式或暂停，不能隐瞒消耗，也不能暗中降低交付标准。

长期方向是让模块责任、契约和项目记忆跨版本持续存在，让具体执行者随任务和模型能力变化。第一阶段仍应先完成一次有限、完整的自动执行，不以长期组织架构研究为由推迟实际交付。

## 二、从用户角度体验完整流程

以下以“为已有网站增加账户中心”为贯穿示例，仅说明目标体验，不代表固定架构、指定技术方案或已经实现的功能。

### 1. 用户描述想达到的结果，而不是先设计团队

用户进入 Team 的 Auto 入口，提供仓库并描述：“给网站增加账户中心，让用户查看和修改个人资料。沿用现有登录方式，保持现有视觉风格，不影响已有功能，先部署到预览环境让我验收。”用户不必预先指定前端、后端和测试各开一个 Session。

Team 先读取已有项目情况，复用已知信息，只询问会影响交付的关键缺口，例如允许修改哪些资料、是否涉及公开信息、视觉参考以及本轮验收范围。普通可逆技术选择可自主判断并记录假设；涉及产品取舍和重要风险时才追问。明确的停止位置是一个能够评审的预览版本，而不是“把整个网站重新设计一遍”。

### 2. 用户看到项目方案，以及有依据的执行方案

Team 把目标整理为需求、范围、设计和验收条件，同时说明准备怎样组织工作。若调查表明变更小且高度相关，可以由当前会话配合少量内部委托完成；若发现几项工作确实能够独立验收和并行推进，再为它们安排独立执行者。

用户看到的不是“采用混合架构”这样的标签，而是能够理解的说明，例如：“先核对用户数据与接口约定；资料编辑界面和已明确边界的接口改动随后并行；共享登录逻辑由一个责任方统一处理；集成后验证读取、保存、错误提示和权限边界。”方案同时说明资源策略、重要未知项和可能触发重规划的情况。这只是本例调查后可能得到的安排，不是所有项目必须遵循的模板。

在必要时，第一段执行可以只进行有限调查，后续工作依据调查结果展开。用户不必为每次范围内的任务展开重新审批，但应能看到组织方案及其重要变化。

### 3. 用户授权运行，Team 完成准备并启动执行

用户审阅本轮结果、权限、资源与检查点后授权 Run，或者明确要求按适用的持续授权执行。Team 核对环境、代码基线、可用能力和工作区，再建立任务与队列记录。执行者先确认自己理解的目标、责任、禁止事项和第一段工作，发现接口或输入不清楚时先解决，而不是直接编码。

启动后的普通分工、等待、验证和修复由 Team 自主推进。用户不需要手动创建每个会话，也不需要在一个执行者完成后再通知另一个开始。无法可靠观测、暂停或恢复的原生能力，应在运行前说明实际限制，不能以看板按钮代替真实能力。

### 4. 用户查看真实进展，不必阅读所有会话

看板以产品目标和检查点为主线，显示当前阶段、任务责任、依赖、最近有效产物、待处理请求、风险和需要用户决定的事项。用户可以展开某项工作，查看相关代码、测试、设计或决策依据，不需要持续盯住所有对话。

如果某项工作没有可靠的新状态，看板显示“状态待核实”及最近证据；如果正在等待接口，显示等待对象和解除条件。它不把“Agent 正在运行”换算成伪精确完成百分比。Team 通过阶段更新呈现有信息价值的变化，而不是把每次工具调用都当成进度报告。

### 5. 出现跨模块需求时，请求排队，而不是打断接收方

资料编辑执行者发现，接口尚未提供已经约定的昵称字段，于是提交协作请求，附上契约、所需结果和对本轮交付的影响。系统先登记并返回请求编号，不要求用户转发消息，也不立刻把新要求插入接口执行者正在进行的工作。

如果接口执行者正在修改登录相关逻辑，调度系统先保留这项请求，并判断它是否阻塞关键交付路径。请求方可以继续处理不依赖该字段的真实工作；相关链路进入明确等待，而不是用占位接口冒充完成。接口执行者到达已保存现场的切换点后，再按队列策略处理请求；必要时，也可以把权限明确、可独立完成的调查分配给其他执行者。

接口结果返回后，系统核对版本和验证依据，更新共享契约或实现状态，并在请求方适合接续时通知它。只有符合依赖要求的结果被接受后，相关工作才恢复。整个过程在看板中可以追踪，用户不需要追问“对方看到没有”。

### 6. 原计划不合适时，用户看到有理由的调整

执行中若发现资料保存和登录状态修改实际上共享同一段强耦合代码，原来的并行边界就需要调整。Team 应保存受影响现场，澄清责任，把相关修改收拢到同一负责人，或者先完成共享部分后再并行展开；不能让两个执行者继续争抢同一文件。

用户看到的是变化原因、受影响范围、可保留成果以及对当前检查点的影响。没有突破原授权时，Team 自动完成调整，不把普通工程协调交回用户。若发现必须新增产品取舍、显著增加资源或执行未授权的高风险动作，则提出一个明确的决策请求，而不是给用户一串没有上下文的错误日志。

### 7. 用户评审实际产物，而不是接受一份完成声明

局部工作通过检查后，Team 按责任顺序集成，验证用户读取资料、修改资料、保存失败、权限和原功能回归等真实链路，再根据风险安排独立审查。实际验证内容以已批准的验收要求为准，不能为了全部显示通过而事后删掉困难部分。

到达预览检查点时，用户得到可运行的产物、变更说明和适用的验证依据，并能看到仍需自己确认的视觉与交互部分。预览部署已在授权内时应实际执行；缺少条件时应明确阻塞，不能用截图或本地构建代替已承诺的预览交付。需要用户认可的条件尚未满足时，应停留在“待用户验收”，而不是已经完成。

如果用户指出设计不符合要求，Team 保留已有结论在原条件下的适用范围，记录反馈并修复相关部分。若用户改变了目标，形成新的需求版本，重新评估受影响工作；不抹掉旧历史，也不无条件重做全部功能。

### 8. 用户结束本轮，或从同一项目继续下一轮

本轮验收后，Team 汇总成果、剩余事项和下一步位置，结束已完成任务并保留必要记录。归档和删除是不同动作，删除工作区或数据仍受相应授权约束。没有下一阶段授权时，不继续扩展范围。

用户之后可以要求“继续做头像上传”或“修复刚才发现的问题”。新一轮从项目事实、当前版本和已有责任中继续，并重新判断是否仍需要同样的团队。即使旧会话已经关闭，也不应要求用户重新讲述整个项目；正在等待或处理中断的请求，应在核对状态后接续，而不是悄悄丢失。

## 三、这一定义如何约束项目推进

### 1. 延续已有机制，补上真实选择与执行能力

当前 `team-plan` 的职责是校验冻结的执行清单并生成任务说明，`team-run` 的职责是准备本地运行产物与派发材料，而不是执行实时任务派发。[^plan][^run] 因此，本定义要求补上的不只是更多提示词，而是组织选择、动态执行、队列调度和可靠状态更新之间的真实连接。

在产品职责上，规划阶段应产出有依据的组织与工作流方案；执行机制应将其转化为受控的真实任务；状态机制应反映队列、依赖、产物和风险；集成、恢复与收尾继续承担版本绑定、失败保留和验收。既有 Skills 可以承接这些职责，但是否拆出新 Skill、增加何种控制程序，应由职责和验证结果决定，不按概念数量机械增加 Agent 或目录。

必须具有可运行的调度机制，不等于必须引入某个队列产品；必须具有动态工作流，不等于必须采用 JavaScript；必须能够共享状态，也不等于一开始就建设大型服务。技术选型可以变化，队列不丢请求、不无故打断、不重复产生副作用、能发现阻塞并恢复的行为要求不能省略。

### 2. 第一阶段交付一条完整链路，而不是若干独立演示

第一阶段应在明确支持的 Codex 环境中，从目标输入开始，贯通需求澄清、组织选择、工作流生成、运行授权、任务派发、协作队列、进度观察、监督纠偏、基本恢复、集成验收和检查点收口。工程内部可以逐步实现，但只跑通某个脚本、只完成离线验证或只画出看板，不代表第一阶段产品已经完成。

真实验证既要覆盖适合并行的任务，也要覆盖小任务不组队、强耦合任务收缩、忙碌接收方收到请求、关键请求长期等待、循环依赖、重复投递、旧执行者迟到返回、中断恢复，以及测试通过但用户链路不满足要求等情况。每个场景都需要真实执行与可核对结果，不能用预设状态动画代替。

第一阶段可以只支持有限运行环境、明确资源和有限检查点；长期自动接替与持续模块团队可以后续增强。但不能把已承诺的队列、监督或基本恢复永久留作愿景，同时把多会话启动演示称为完整自动化。

### 3. 分开判断产品结果、运行可靠性和团队收益

产品是否满足需求，Team 是否按预期运行，以及多会话是否比其他执行方式更有价值，是三个不同问题。产品完成但依赖大量手工绕过，不算 Team 全链自动执行成功；流程记录完整但用户目标未实现，也不算交付成功。[^baseline-eval]

对照应包含允许合理使用 Subagent 的单个 Codex Session，以及人工管理多 Session 的方式；在相同目标、代码起点、工具和可比资源条件下，比较缺陷与遗漏、总耗时、资源消耗、返工和用户介入。还应分别观察架构选择、动态工作流和队列调度的收益与开销，避免把更多计算换来的结果误认为组织方法本身的进步。

初始选择策略从研究和项目证据出发，后续用运行数据校准。不需要为每个用户任务完整试跑所有架构，也不能在没有数据时宣布已经拥有可靠的最优架构预测器。模型和环境变化后，原有选择依据应重新评估；组织机制必须允许简化，不把已建设的复杂度当成继续使用它的理由。

**Codex Team 最终要证明的是：用户委托目标之后，系统能够选择合适的组织方式，按真实依赖安排工作，在不必要打断执行者的前提下完成协作，并通过验证和有依据的调整持续接近交付，而不是只让更多 Agent 同时忙碌。**

## 依据与适用边界

本版本延续已确认的 Auto 入口、动态执行层级、共享事实、监督验收和长期交接需求；新增把研究支持的组织选择、可执行动态工作流和队列调度确立为完整产品链路的一部分。具体优先级算法、状态存储方式、工作流语言、控制程序部署形态以及原生安全切换能力，不在本文中假定已经确定或实现。

研究与产品文档提供参考依据；本文提出的项目级排队规则、版本化重组和恢复要求，是 Codex Team 的设计约束，不是引用来源已经证明在 Codex Team 中有效的现成实现。来源中的数值结果、可用功能和接口，也不能直接替代本项目的实测。
