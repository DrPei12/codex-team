# 08. 模型、Thinking 与上下文策略

## 两个需要避免的极端

极端一：所有任务都使用最高能力、最高 thinking，质量可能稳定但成本和延迟过高。

极端二：认为主编排者只要写出“极其详细的 prompt”，低能力 worker 就一定能可靠完成。详细 prompt 可能造成信息淹没，也无法补足跨文件推理、异常诊断或新情况判断能力。

第一版采用结构化 briefing + 分级模型 + 明确升级条件。

## 按认知难度分配，而非按职位名称硬编码

### 高认知任务

- 项目架构、依赖切分、跨模块权衡；
- 不完整需求下的计划；
- 安全/数据风险判断；
- 证据冲突和复杂故障归因；
- 多 worker 结果综合和最终验收。

这类任务由当前可用的高能力模型和较高 thinking 承担。用户提出的 `sol-max/ultra` 可作为实验候选，但具体模型名、档位和可用性必须在运行时核验。

### 中等认知任务

- 已有契约下的模块实现；
- 有明确测试的重构；
- 常规 code review；
- 生成结构化 artifact。

可以使用成本更低的常规模型，但要允许遇到升级条件时返回主编排者或切换更强模型。用户提出的 `luna-max` 属于候选思路；在确认 Codex 当前是否提供该配置前，不能写成默认事实。

### 低认知任务

- 精确搜索、清单核对、格式转换；
- 运行确定命令并收集结果；
- 机械更新多个独立文件；
- 小范围、强测试约束的实现。

优先交给 subagent 或低成本 worker，避免消耗主编排者上下文。

## Worker 自升级条件

任何低/中档 worker 遇到以下情况应停止扩张并上报：

- task brief 与代码事实冲突；
- 必须改变公开 contract；
- 修改范围将越过所有权边界；
- 出现多个合理架构选择且取舍影响全局；
- 测试失败不能用局部原因解释；
- 涉及权限、数据删除、迁移、外部写操作；
- 证据不足却只能靠猜测继续。

升级并不总是更换模型，也可以是请求主编排者澄清、建立 reviewer 或重新切分任务。

## Prompt 原则

结构化优于冗长：

- 把目标、范围、所有权、输入输出、Gate 和升级条件做成字段；
- 背景材料给路径、revision 和读取顺序；
- 只提供当前角色需要的全局信息；
- 明确禁止事项和完成定义；
- 给一个正确 artifact 示例优于几千字泛泛指导。

Prompt 长度本身不是质量指标。后续评测应比较：短结构化、长叙述、结构化 + 按需 references 三组。

## 单任务“最高有效上下文”

不存在一个仅由 token 数决定、对所有任务通用的断崖。研究和实际使用通常显示：随着上下文增长，检索位置、干扰信息、旧假设、任务切换和多轮错误累积都会影响表现；模型即使没有超过硬 context window，也可能出现有效性下降。

因此应测“上下文健康”，而不只数 token：

- 对最新 spec 的准确引用率；
- 是否重复已经完成的探索；
- 是否把被替代决策当成当前决策；
- 首次执行成功率和返工率；
- handoff 信息遗漏率；
- 单任务每轮有效产出与等待时间；
- 主编排者纠错次数。

## 轮换触发器

以下信号组合出现时，考虑把长期任务 compact、rehydrate 或 handoff 给新任务：

- 多次遗忘或混淆当前 contract；
- 开始反复读取同一批文件却没有新结论；
- 多阶段职责混在一个历史中，旧指令持续干扰；
- 返工率或无关输出明显上升；
- 项目已到自然里程碑，可形成稳定交接包；
- 上下文接近产品限制。

不能只靠固定“第 N 轮就换人”。任务复杂度、每轮信息量和 compaction 行为不同。

## 待做对照实验

1. 高能力编排者 + 常规模型 worker，对比全员高能力；
2. 短结构化 brief、长详细 prompt、按需 references；
3. 同一 worker 连续 1/3/5/8 个同类任务，对比每次 fresh task；
4. 长期 owner、压缩后的 owner、rehydrated 新 owner；
5. 低能力 worker 遇到异常时是否能正确升级；
6. 相同质量下的 wall time、token、返工和用户介入次数。

Token 记录当前不是 Phase 0 的阻塞项，但评测框架应预留导入外部 telemetry 的字段，不伪造产品未提供的数据。
