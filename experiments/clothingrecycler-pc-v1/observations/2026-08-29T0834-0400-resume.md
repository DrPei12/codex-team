## Team skill 实战反馈

### F-001：ownership 语义跨 phase 不闭合

**行为证据：** 产品 run 的一个 lane 使用裸 `write_paths` 值 `docs/design/pc-ai-native-v1` 表达目录所有权。该 manifest 已通过 plan/run；到 `team-recover candidate` 时，真实子文件被判 ownership violation，且 candidate 未生成。主编排后续也报告同类问题阻止 `team-integrate candidate`。

**源码核对：** 当前 `team-recover.py` 与 `team-integrate.py` 均用 `fnmatch.fnmatchcase` 直接匹配 pattern；裸路径只匹配同名文件。现有目录测试使用 `owned/**`。`manifest-fields.md` 没有清楚说明裸路径是精确文件、目录必须写 `/**`。

**当前结论：** 已证明的是 plan 接受的 ownership 表达与后续 candidate phase 的解释产生语义/验证缺口。不能只凭这次行为断言 runtime helper 单方面错误，也不能把产品 manifest 的错误表达忽略掉。

**改进候选：**

1. 在 manifest reference 明确 glob 语义和目录写法；
2. validator 对疑似目录裸路径 fail closed，或由 canonical generator 显式规范化为 `/**`；
3. plan、integrate、recover 共用一个 ownership matcher，并增加裸路径、`dir/**`、单文件、Windows alias 的跨 phase 回归；
4. 修正前保留本 run 的失败输入、stderr、无 candidate 事实作为 RED corpus。

### F-002：reasoning policy 无法在 Open Design 边界验证

- Local Codex/Open Design 能选择 `gpt-5.6-luna`，但当时接口没有设置或回读 reasoning effort 的字段。
- 把 `max` 写进 prompt 不构成 effective 配置证据。
- 原 run 因此按 frozen stop condition 阻塞，随后采用人工设计 fallback；该 fallback 不能计为 Open Design generation 成功。
- 改进方向应是让 manifest/receipt 分开保存 `requested_model/reasoning`、`effective_model/reasoning` 与 `observability`，允许策略明确选择“unverified inheritance 是否可接受”，而不是把不可观测值硬写为 mismatch 或 success。

### F-003：Shell 包装可能掩盖内层失败

- application-core worker 报告一次 PowerShell 包装命令未实际启动测试，但外层退出码为 0；worker 主动识别后才重跑正式 Gate。
- 这证明 Gate receipt 不能只信最外层 process exit；还要绑定实际 command、预期日志/测试结果存在性，以及 fail-closed wrapper 行为。
- 后续 Team 改进应增加“内层命令未运行但 wrapper exit 0”的负例，要求 receipt 检查预期证据文件或机器结果计数。

### F-004：人工 fallback 与 canonical 状态衔接

- Open Design run 失败后，主编排者先尝试 `team-recover`，因 F-001 无法生成合法 candidate，随后手工 successor 和人工设计 fallback。
- 实现可以继续，但 canonical status 不能把手工 fallback 重标为原 Open Design lane 成功。
- 需要显式表达 `manual-fallback-accepted`、被替代 Gate、仍未验证的原能力，以及后续 integration/review 如何消费该替代证据。
